# 能力中心－工作流：会话展示运行时评审

> 评审范围：只看中间会话／消息流；完全不评审右侧面板。日期：2026-08-01。仅做源码静态审计，未修改项目代码、未运行测试。

## 0. 结论先行

**结论：现有 `ToolPresentation + PresentationBlock` 足以当“叶子渲染原语”，不足以复现 demo 的真实运行行为。缺的不是再给 ToolBlock 加标题，而是其上一层的、可持久化的“会话呈现运行时”：稳定 turn/anchor、独立呈现事件、确定性顺序、create/update/terminal 生命周期、visibility/prominence、交互绑定，以及同一事件对 live WS 和刷新 REST 的双投影。**

父方案“只扩展 `ToolPresentation.display/prominence`”应明确否决为完整方案：它最多把**某一次工具调用**做成更醒目的卡片，无法表达无工具的业务结论、工具之间的叙事、独立业务组件、审批生命周期，也无法修复当前 live WS 丢失 `presentation`、刷新后才出现的事实差异。可保留它作为 P0 兼容修补，但不能把它命名为 demo parity。

当前最关键的事实：

1. demo 直接把脚本 `ApiTranscriptBlock[]` 喂给 `mapSessionDetailToMessages`，绕过模型、durable event、WS、transcript parser；`defaultOpen` 和 `presentation` 因此天然可控（`web/src/components/scenarios/replay/ScenarioReplayView.tsx:145-155,178-196,288-322`）。
2. 仓内没有 `scenarioToTranscriptBlocks` 符号；实际等价投影是 `buildStep` / `presentationToReplayScript`（`web/src/components/scenarios/replay/presentationReplayScript.ts:491-503,641-645`）。它生成的是 `ToolPresentation`，并没有给脚本注入 `display`；全仓 replay 生产脚本中没有 `display:`。审批则是 ReplayView 自己追加的组件，不走真实消息协议（`ScenarioReplayView.tsx:328-360`）。
3. real refresh 路径能从 `tool_result.presentation` 恢复 `ToolPresentation`，但 real live WS 的 `tool_result` 明确不带 presentation（`server/src/channels/web/channel.ts:4067-4077`; `server/src/channels/web/wsTypes.ts:164-166`）。这已经证明“嵌套在 ToolPresentation 里”没有 live/refresh 同构。
4. `PresentationBlock` 已经有受控闭集 `callout | records | gate`，方向正确（`shared/src/lib/presentation/types.ts:19-81`），但它目前只是 `text.display` 外挂；server transcript parser 不产出 `display`，也不存在 presentation durable/WS event。
5. demo 自己把动态 catalog 投影标成 `producer: "fallback"`、`state: "needs-change"`，说明它是合成演示，不是 runtime 能力证明（`presentationReplayScript.ts:623-638`）。

本报告没有使用官网定位、营销稿或外部社区材料；任务要求“只读源码”。对**实现行为**，可执行类型、switch 分支和调用链是直接证据；测试是次一级的预期证据；注释只作为低权重设计意图，若与接线冲突，以接线为准。例如 `PresentationBlock` 注释声称覆盖 demo，并不等于 live/refresh 已接通（`shared/src/lib/presentation/types.ts:3-16`）。因此不存在需要外部独立验证的商业结论，但也不把源码注释中的“覆盖 25 种块”当成已上线事实。

## 2. demo 的真实路径：为什么它看起来丰富、直观、受控

### 2.1 ReplayScript 已经是“排好版的会话结果”

`ReplayScript` 的 step 直接携带 `blocks: ApiTranscriptBlock[]`，并另带 approval 后续块（`web/src/components/scenarios/replay/types.ts:19-30,68-70`）。`ScenarioReplayView` 每步把这些 block 追加到本地 state，再构造假的 `ApiSessionDetail` 调共享 mapper（`ScenarioReplayView.tsx:145-155,178-196`）。因此 demo 使用了真实的**末端 mapper/renderer**，却没有使用真实的**运行时生产、持久化和传输**。

调用入口也是直接切换到 replay：`web/src/components/scenarios/ScenariosPanel.tsx:227-235`。

### 2.2 `defaultOpen` 是脚本作者直接注入，不是运行时策略

动态 projection 对入口和关键工具逐块写 `defaultOpen`：入口 `true`（`presentationReplayScript.ts:505-519`），读取工具 `false`（`:528-543`），行动工具 `true`（`:560-576`）。共享 mapper 把 tool block 的 `defaultOpen` 改名为 message 的 `defaultExpanded`（`shared/src/lib/sessionsApi.ts:376-397`）。`groupMessages` 又只在 `defaultExpanded && presentation` 时把工具从 activity group 提升为主流独立行（`shared/src/lib/groupMessages.ts:13-21,85-108`）。

这套规则的测试还明确写着：只有 presentation 没有 `defaultExpanded` 的真实工具仍被收进活动组（`shared/src/lib/groupMessages.test.ts:42-65`）。而 real transcript parser 创建工具块时没有设置 `defaultOpen`（`server/src/data/transcripts/parse.ts:374-421`）。所以当前“关键动作上主流”是 demo 注入，不是现实会话的服务端决策。

### 2.3 demo 的业务密度主要来自 `ToolPresentation.detail`

projection 把一章拆成“感知／行动”两条工具执行行，并手写 title、detail、status（`presentationReplayScript.ts:522-576`）；字段网格、警告、判定等由 `DetailLine` 变体表达（`:459-488`；类型见 `shared/src/lib/toolPresentation.ts:20-78`）。这确实比仅有标题摘要丰富，但语义仍绑定到一次 `tool_use`。

### 2.4 交互卡不是同一消息协议

审批前，projection 只在 step 上写 `approval` 配置（`presentationReplayScript.ts:579-617`）。ReplayView 在消息列表之后单独渲染 `ReplayInteractionCard`，批准／拒绝后再追加脚本块（`ScenarioReplayView.tsx:328-360`）。它不是 `ApiTranscriptBlock`，也不是 durable interaction 的投影。换言之，demo 的“可交互”不能作为真实 `PresentationBlock.gate` 已打通的证据。

### 2.5 `display` 协议存在，但 demo 脚本目前没有使用

`ApiTranscriptBlock` 允许 `display?: DisplayBlockSpec[]`（`shared/src/types/session.ts:255-265`），`mapSessionDetailToMessages` 只在 `kind === "text"` 分支 normalize 后放入 message（`shared/src/lib/sessionsApi.ts:286-296`），`MessageItemWithDisplay` 再渲染成 `PresentationBlocks`（`web/src/components/MessageItemWithDisplay.tsx:17-36`）。但 replay 各生产脚本没有 `display:`，动态 projection 也只产 ToolPresentation。因此不能把“类型已经存在”误判成“demo 已经由 presentation protocol 驱动”。

## 3. 真实会话的端到端路径与断点

### 3.1 工具执行与 durable event

真实工具返回值可携带 server 生成的 `ToolPresentation`（`server/src/agent/toolRuntime.ts:209-222,1544-1560`）。Raw loop 把它写入 `tool_result` PlatformEvent（`server/src/runtime/rawAgentLoop.ts:1662-1678`）；PlatformEvent 的工具结果类型也含 `presentation`（`server/src/runtime/types.ts:505-545`）。append 先写 EventStore，再做 legacy transcript projection（`rawAgentLoop.ts:2962-2965`）。

这条链的信任边界尚可：默认 presentation 由 server 的 `buildToolPresentation` 生成，provider 也只能从 server provider 返回（`toolRuntime.ts:1544-1560`），不是模型直接输出任意前端组件 JSON。但当前 builder 主要是通用工具摘要，没有承载 demo 的 turn-level 业务编排。

### 3.2 live WS：presentation 在服务端适配时被丢掉

存在两条 web 输出适配，二者都丢 presentation：

- durable PlatformEvent adapter：`tool_result` 只下发 `toolId/toolName/content/result/isError`（`server/src/channels/web/channel.ts:4067-4077`）；
- runtime outbound adapter：`tool_result` 同样只发 result/isError（`channel.ts:3722-3733`），而 `OutboundEvent` 工具结果类型本身没有 presentation（`server/src/types/index.ts:48-77`）。

WS union 也没有 presentation/presentation event（`server/src/channels/web/wsTypes.ts:155-182`；共享客户端 union 同样见 `shared/src/types/ws.ts:109-137`）。前端 `processWsEvent` 对 tool started/completed/result 只创建或更新工具运行状态与 raw result（`shared/src/lib/wsEventProcessor.ts:414-503`），没有任何 display/presentation 分支。

**直接后果：同一工具在流式阶段不能显示 server 已经生成的 ToolPresentation；刷新后才可能显示。这不是视觉问题，是协议丢字段。**

### 3.3 refresh：legacy transcript 可以恢复 ToolPresentation

legacy projection 把 `tool_result.presentation` 写入 JSONL（`server/src/runtime/legacyTranscriptProjection.ts:186-200`）。会话详情 API 以 JSONL parser 为正文主源：`buildSessionDetailSnapshot` 调 `parseTranscriptFile`，EventStore 这里只补活动时长和 run state（`server/src/routes/sessions.ts:761-825,847-859`）。parser normalize presentation，并回填到匹配的 tool_use（`server/src/data/transcripts/parse.ts:374-421`）。

浏览器加载详情后：

1. `web/src/lib/sessionsApi.ts:41-56` 调共享 `mapSessionDetailToMessages`；
2. mapper 把 ToolPresentation 和 defaultExpanded 放进 tool message（`shared/src/lib/sessionsApi.ts:376-397`）；
3. `groupMessages` 聚合 activity（`shared/src/lib/groupMessages.ts:110-169`）；
4. 独立消息由 `MessageItemWithDisplay` 渲染 display，工具由 `ToolBlock` 渲染 ToolPresentation（`web/src/components/MessageItemWithDisplay.tsx:17-36`; `web/src/components/ToolBlock.tsx:133-169,240-287`）。

server parser 从未给任何文本块产出 `display`；`ApiTranscriptBlock.display` 目前只是 API 类型/手工 fixture 能力。因此真实刷新也没有独立业务 presentation 的来源。

### 3.4 grouping 会吞掉“只加 presentation 的工具主流感”

activity type 固定包含 `tool_use`（`shared/src/lib/groupMessages.ts:13-21`）。只有 `defaultExpanded && presentation` 才提升；real parser 没有 defaultOpen，所以真实 ToolPresentation 通常仍在 activity group 里。`ActivityGroupBlock` 自己直接渲染 `ToolBlock`，不是 `MessageItemWithDisplay`（`web/src/components/ActivityGroupBlock.tsx:1-10,268-349`）。当前方案因此无法靠“presentation 有内容”自动得到 demo 的主流布局。

### 3.5 interaction 的 live/refresh 也不是统一 timeline

durable 类型已有 `interaction_requested/interaction_responded`（`server/src/runtime/types.ts:736-773`），但 transcript detail block union没有 interaction kind（`shared/src/types/session.ts:234-271`）。live 收到 `interaction_event` 后，前端只是重新拉 pending interactions（`shared/src/lib/wsEventProcessor.ts:548-564`; `web/src/hooks/useChatAppState.ts:2044-2060`）；历史 AskUser 又靠 tool transcript 特判重建（`shared/src/lib/sessionsApi.ts:94-118`）。这不足以支撑 demo 那种“门禁卡在确定位置、状态随响应更新、刷新后仍在原位置”的业务展示。

## 4. 能力边界：叶子组件够，运行时不够

| 能力 | 当前 ToolPresentation | 当前 PresentationBlock | demo/真实运行所需 | 判定 |
|---|---|---|---|---|
| 单次工具的人类摘要 | title/detail/status | 不负责 | 是 | 基本够 |
| 受控业务卡片闭集 | detail 原语 | `callout/records/gate` | 是 | 叶子够 |
| 普通叙事后独立插块 | 绑定 tool | 只能挂 `text.display` | 是 | 无生产/事件路径 |
| 无工具 turn 的业务结论 | 不可表达 | 类型可表达 | 是 | 无独立 timeline item |
| 多工具之间的确定性编排 | 无 | 无 | 是 | 缺 turn composition/order |
| create→update→terminal | 只有最终 status | block 无 id/revision/status | 流式必需 | 缺 lifecycle |
| stable anchor | toolId 隐式 | 挂某个临时 message | 刷新/重连必需 | 缺 turn/message/tool anchor |
| visibility/prominence | 无 | 仅 block 内 `defaultOpen` | 主流/折叠策略必需 | 缺 envelope 级策略 |
| live/refresh 同构 | live 丢失 | 无 WS/durable event | 必需 | 不成立 |
| 审批回写 | 不负责 | gate 有 action | 必需 | 接线不安全且不完整 |

尤其要注意：`DisplayBlockSpec` 只有 `kind/data`（`shared/src/lib/presentation/registry.ts:180-199`），没有 blockId、revision、anchor、sequence、lifecycle、visibility 或 prominence。它是**快照内容协议**，不是运行时协议。

`PresentationBlock` 的动作接线也不能直接作为生产方案：wrapper 把“label 恰好等于 `拒绝`”解释成 false，其余全部解释成 true（`web/src/components/MessageItemWithDisplay.tsx:22-29`）。动作语义不应由中文文案推断。normalizer 对 link 只 clamp 文本、不校验 URL scheme（`shared/src/lib/presentation/registry.ts:59-77`），渲染器直接放入 `<a href>`（`web/src/components/presentation/PresentationBlocks.tsx:43-55`）。在扩展生产使用前必须补 capability binding 与 URL allowlist。

## 5. 最小但完整的技术方案

### 5.1 新增上一层协议：`ConversationPresentationV1`

不做任意 row/column DSL，不让模型输出 React/HTML/UI JSON；保留现有三个 `PresentationBlock` 作为闭集叶子。新增固定 envelope：

```ts
interface ConversationPresentationV1 {
  protocol: 'conversation-presentation/v1';
  presentationId: string;       // 全 session 稳定
  revision: number;             // 单调递增、幂等
  sessionId: string;
  runId: string;
  turnId: string;               // 建议 `${runId}:${turnIndex}`，持久化而非前端推导
  anchor:
    | { kind: 'turn'; turnId: string }
    | { kind: 'message'; eventId: string }
    | { kind: 'tool_call'; toolCallId: string }
    | { kind: 'interaction'; interactionId: string };
  placement: 'decorate-anchor' | 'before-anchor' | 'after-anchor' | 'standalone';
  slot: number;                 // create 时固定；update 不移动
  lifecycle: 'pending' | 'ready' | 'failed' | 'cancelled';
  visibility: 'conversation' | 'hidden';
  prominence: 'ambient' | 'normal' | 'primary';
  narrative?: { text: string; format: 'plain' | 'markdown' };
  blocks: PresentationBlock[];  // 继续走闭集 normalizer
  producer: {
    kind: 'server-adapter' | 'workflow-template';
    key: string;
    version: string;
  };
}
```

设计要点：

- `ToolPresentation` 继续描述一次工具；不要把 turn-level `display` 硬塞进它。
- `decorate-anchor` 可把某工具设为 primary/default-open；`standalone` 负责工具之间或最终结论的业务卡。
- `narrative` 只允许 server/workflow 模板产生，用于 demo 的普通叙事节奏；模型正文仍走现有 text stream，不从模型文本解析 UI JSON。
- `slot` 是 turn 内固定布局序号；EventStore `sequence` 决定全局创建先后，revision update 只原位更新。
- `prominence` 属于会话 composition envelope，而不是 ToolPresentation leaf；groupMessages 根据它做确定性提升，不靠前端猜测 presentation 是否“重要”。

### 5.2 只需两个 durable 事件类型

用全量快照 upsert，避免 patch 顺序和旧客户端 merge 语义：

```ts
type PlatformEvent +=
  | { type: 'conversation_presentation_upserted'; presentation: ConversationPresentationV1 }
  | { type: 'conversation_presentation_removed'; presentationId: string; revision: number; reason: string };
```

pending/ready/failed/cancelled 均由 upsert 的 lifecycle 表达；每次 update 携带全量、经 server normalize 的 snapshot。EventStore eventId/sequence 是投影 cursor。相同 `(presentationId, revision)` 幂等，低 revision 丢弃。通常不物理 remove，terminal upsert 保留审计；removed 只用于策略撤回/脱敏。

交互不要发自由动作 JSON：`GateBlock` 的 server projection 必须引用同 session 中真实 durable `interaction_requested` 的 interactionId；action 增加明确 `intent: 'approve' | 'reject' | 'submit'`，前端不得从 label 推断。`interaction_responded` 到达后，由 projector upsert 同一 presentation 为 terminal/read-only。

### 5.3 受信生产，而非模型自绘 UI

新增 `ConversationPresentationPolicyRegistry`：输入是 `{workflowVersion,nodeId, typed tool result, durable interaction/domain event}`，输出上述固定 envelope。只有两类 producer：

1. 编译过的 workflow template：模板在发布工作流时过 JSON Schema/Zod 校验，只允许固定 block kind 和受限数据绑定；
2. server tool/domain adapter：像现有 `buildToolPresentation` 一样在可信 server 代码内把业务结果映射为 blocks。

明确禁止：从 assistant text 中提取 fenced JSON、让模型调用通用 `render_ui` 工具、透传 connector 返回的 `kind/actions/href/interactionId`。所有 text clamp、条目上限沿用 normalizer；新增 URL scheme allowlist（https/受控相对 artifact URL）、interaction capability 校验、同 session/tenant 校验和 producer/version 审计字段。

### 5.4 同一个 durable 事件，双投影而不是两套逻辑

**写入顺序**：runtime 先 append `conversation_presentation_upserted`，成功后才能对外可见；不要先发 WS 再落盘。现有 raw loop `append → transcriptProjection` 结构可复用（`rawAgentLoop.ts:2962-2965`）。

**live 投影**：

- `channel.ts` 把 durable presentation event 原样（去掉 server-only producer 内部字段亦可）映射为 `WsServerMessage { type:'conversation_presentation', cursor, presentation }`；
- shared `wsEventProcessor` 按 id/revision upsert `MessageItem type:'presentation'`，按持久化 slot/anchor 排序；
- 重连使用现有 durable cursor 重放，同 revision 不重复。

**refresh 投影**：

- `legacyTranscriptProjection.ts` 为 presentation event 写独立 JSONL line，保留 eventId/sequence/revision；
- `parse.ts` reducer 按 id/revision 生成 `ApiTranscriptBlock kind:'presentation'`，保留第一次 slot 位置，后续更新不追加副本；
- 长期应让 `buildSessionDetailSnapshot` 直接从 EventStore 做 conversation projection；最小迁移期可继续以 JSONL 为 base，但必须加 event-log fallback/merge，避免 projection 文件短暂落后；
- `mapSessionDetailToMessages` 把它映成独立 presentation item。live 和 refresh 共用同一个 reducer 函数并做状态等价测试。

**现有 ToolPresentation P0 修复**：立即给 WS `tool_result` 增加 `presentation?: ToolPresentation`，在客户端 normalize 后更新对应 tool message。这只能修当前丢字段和刷新闪变，不能替代独立 presentation event。

### 5.5 前端 timeline 与交互

- `MessageItem` 增加 `type:'presentation'`，不伪造成空 text，也不必须寄生某个 tool。
- `groupMessages`：presentation item 永不进入 activity group；`decorate-anchor + primary` 的 tool 由 projector 明确提升，normal 工具保持现状。
- `MessageItemWithDisplay` 保留做 legacy `text.display` 兼容；新 item 直接渲染 `PresentationBlocks`。
- `BlockContext.onAction` 改为接收 `{interactionId, intent, actionId}`；调用现有 interaction respond 通道，server 再校验 capability。resolved/failed 状态来自 durable event，不由点击后的本地乐观文案充当真相。
- Replay demo 最终也应把脚本输入先通过同一个 policy/event reducer，再交 MessageList；移除 `ReplayInteractionCard` 特供路径。否则 demo parity 测试永远只能证明 UI，不证明 runtime。

## 7. 验收测试（必须形成阻断门槛）

### A. live / refresh 状态等价

1. 固定事件序列：message start/end → tool started → presentation pending → tool result → presentation ready → run finished。
2. 路径一经 `channel.ts → wsEventProcessor` 得 live messages；路径二经 `legacyTranscriptProjection → parseTranscript → mapSessionDetailToMessages` 得 refresh messages。
3. 去掉纯瞬态 `streaming` 后，断言 item id、顺序、anchor、blocks、lifecycle、prominence 完全相等。
4. 单独回归当前缺陷：ToolPresentation 在 tool_result 到达当刻可见，刷新后无闪变、无重复。

### B. lifecycle / 重连 / 幂等

- pending rev1、ready rev2、迟到 rev1、重复 rev2：只保留 rev2，位置不移动。
- WS 在 rev1 后断线，按 durable cursor 重放 rev2：原位更新，不新增长卡。
- 进程在 durable append 成功、WS 发送前崩溃：刷新和重连都能恢复；append 失败时 live 不可见。
- failed/cancelled terminal 刷新后仍保留失败原因，不退回 loading。

### C. 顺序与 grouping

- turn narrative → normal tool group → standalone records → primary decorated tool → gate → final callout 的顺序 live/refresh 一致。
- normal tool 仍聚合；primary tool 独立；standalone presentation 永不被 activity group 吞掉。
- 并行工具、重试、无工具 turn、多个 presentation 更新均不依赖 `Date.now()` 临时 message id。

### D. 交互

- gate action 带明确 `approve/reject` intent；中文、英文、改文案都不改变语义。
- 点击只发送一次；interaction resolved 后同一卡变 read-only；刷新后仍在原 slot 且显示已批准/已拒绝。
- cross-session/tenant interactionId、已 resolved id、伪造 actionId 均由 server 拒绝。
- Replay demo 不再用 `ReplayInteractionCard`，同一用例同时覆盖真实 interaction respond 通道。

### E. 安全与兼容

- 模型输出 ```json {"kind":"gate"...}``` 只按正文显示，绝不生成 presentation。
- connector/tool raw result 中夹带未知 kind、`javascript:` URL、任意 interactionId 均被丢弃；https/受控 artifact URL 正常。
- 超长 body/items/actions 被 clamp；未知新 block kind 在旧客户端静默降级，不让整条会话崩溃（现有未知 kind 行为在 `shared/src/lib/presentation/registry.ts:190-198`）。
- 老 transcript 没有 presentation event 时逐像素保持现状。

### F. demo parity

把 25 类 demo 形态做成 producer fixtures，不直接给 ReplayView 塞 `ApiTranscriptBlock`；每个 fixture 均走 durable event → live 与 refresh 两条链，并做 DOM/visual snapshot。验收关注中间会话，不依赖任何旁侧区域。尤其覆盖字段网格、缺口警告、判定清单、records、gate、行动回执、普通叙事与多步骤顺序。

## 8. 对父方案的最终判定

**否决“仅扩展 `ToolPresentation.display/prominence` 就能达到 demo 程度”。**

可确认的部分只有：

- `display` 叶子组件和 `prominence` 提升提示，能把一条工具执行做得更像 demo；
- P0 把 ToolPresentation 补进 WS，能修掉一个明确的 live/refresh bug。

但它无法解决：

1. demo 的叙事／业务卡并不总属于某个工具；硬挂工具会在无工具、并行工具、重试时失去语义 anchor；
2. 当前 ToolPresentation 到 live WS 已经丢失，扩字段只会继续丢；
3. 没有 presentationId/revision/lifecycle，流式 update、重连幂等、失败终态都不可定义；
4. 没有 turn-level slot/sequence，工具、叙事、业务卡、交互无法确定编排；
5. `defaultOpen` 是 demo block 的客户端提示，真实 parser 不产，prominence 若仍由前端猜测会重演同一问题；
6. 审批需要 durable interaction 绑定和 terminal projection，不是一个可点击标题；
7. 把 turn presentation 塞进 ToolPresentation 会模糊现有清晰分工，并迫使所有业务展示伪装成工具结果。

准确定位是：**ToolPresentation 与 PresentationBlock 都应保留；新增其上方的 `ConversationPresentation` 事件／投影／timeline runtime。** 这才是最小且完整、可流式、可刷新、可审计、且不允许模型自由绘制 UI 的方案。
