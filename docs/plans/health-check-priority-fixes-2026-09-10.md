## 目标与完成口径

总体方案不遗漏其他高优先级条目，但本轮执行范围收敛为 REL-01、REL-02、UX-03。每项只有同时满足以下条件才能在进度文件中标记“已修复”：

1. 在当前基线仍可证明问题存在，或明确记录已由后续提交解决/条件不适用的证据；
2. 修复真实权威路径，而不是只在调用方吞错、重试或修改测试；
3. 新增修复前失败、修复后通过的最小回归，并保留既有安全反向断言；
4. 通过受影响工作区的类型检查、单元/故障注入测试和构建；
5. 完成对应的本地端到端验证，并在进度文件记录命令、结果和限制；
6. 涉及真机、生产代理、多进程共享存储或最终签名制品的项目，代码修复与环境验收分开记录，不用本地模拟冒充生产验收。

## 实施顺序

1. 先做当前代码复核，冻结每项实际调用链、已有保护和失败样例。
2. 优先完成边界清晰且可独立验证的 D/SEC-04、F、B/UX-02、G。
3. 再完成 A，共享同一 mutation/lock 契约，避免 UserStore 与 AuthEpoch 各自形成不同语义。
4. 完成 C，并使用真实文件系统适配器验证账号切换、退出、锁定和迟到下载。
5. 完成 E；以本地 PostgreSQL 16 的独立测试库执行跨进程锁丢失、滚动路径和故障恢复 E2E。
6. 完成 D 的 HTML/内部路由部分以及 H 的本地发布门槛；需要现网或真机证据的状态保持“待环境验收”。
7. 运行全量受影响检查、构建和端到端矩阵，更新进度台账，提交本地 Git commit。
