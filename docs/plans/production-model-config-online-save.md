# 生产模型配置在线保存与生效

> 2026-09-10：工具、提示语、轮询、生图、STT、环境池与 Codex 已沿用本协议，并增加服务端 operation scope。模型保存仍保留原能力与字段边界；完整清单见 `platform-admin-controlled-config-save-inventory.md`。

PR #593，2026-09-09。本文描述已接入的运行代码，不再是只禁用生产保存按钮的第一阶段方案。代码提交、测试通过不等于已经部署生产；本 PR 不自动合并、部署或修改线上配置。

## 管理员操作

生产平台模型页修改配置后，点击“保存并生效”并确认生产提示。请求携带当前 `expectedRevision` 和相同版本的 `productionConfirmation`。服务端完成持久化及 API、Worker 两端的精确版本读回才返回成功，页面在此之前不显示“已保存”、不允许重复保存。

不增加 Draft、审批或跨环境晋级页面。保存只修改当前环境，不复制 Staging 配置或凭据到 Production。API Key 留空继续表示保留；新密钥写入当前环境 Vault，响应不回显明文。

后端发布器未初始化、缺少活动进程或仍在恢复时，页面显示服务端不可写策略与具体原因，保留浏览和独立授权入口，不再用静态“尚未实现”代替实际运行状态。

## 首次启用

目标部署为现有 Linux 单主机、蓝绿 API（`ws-only`）和 Runtime Worker（`runtime-worker`）。两端需运行同一 Server 制品，拥有明确 production 身份、releaseId、发布绑定的 ConfigIdentity，以及正确的 systemd 活动颜色、PID 和私有摘要路径。

正常受控 App 发布持有配置治理锁后，从已验证目标制品运行 `dist/config-publication-cli.js prepare`。它只为当前配置初始化签名基线、密钥和快照，不改变模型值、不迁移 Vault 或重新授权。已有有效基线只验证，不重建或默许漂移。CLI 随 Server dist 进入密封制品。

新 API/Worker 启动并生成有效回执后，模型 GET 返回 `writePolicy.canSave=true`。因此需要先按原发布流程部署包含本 PR 的版本；只合并、只发布 Web 或手改运行环境变量不是启用方法。Runtime、GET、健康检查及刷新不会自行初始化或重绑定信任。

## 事务与可信版本

`.release.env` 保留不可变的代码发布基线。`/etc/agent-saas/config-publications` 保存权限为 0700 的目录和 0600 的 Ed25519 密钥、签名 current 记录、追加事件、完整 JSONC 快照。该目录含敏感配置，不能公开、提交 Git 或上传公共 artifact。

在线保存执行以下步骤：

1. 持有现有配置治理锁与生产主机锁 `/run/lock/agent-saas/promotion.lock`，直至读回或补偿完成，避免与代码推广、切色同时前进。
2. 在候选凭据和文件副作用之前校验 CAS、生产确认、签名基线及两端当前应用状态。客户端不能选择环境、文件路径、密钥或 Worker 目标。
3. 校验候选的真实内容与辅助模型引用、Schema、受管凭据版本。范围仅限 `models`、`memory.index`、`titleGenerator`、`guardrail`、`systemPrompts.utility.title`；不能仅信任客户端声明的 changedPaths。
4. 先持久化前后快照与签名 `applying` 意图，再原子替换配置。事件、头和快照使用 fsync 与原子 rename。
5. API、Worker 分别通过共享刷新事务应用模型解析器、价格、辅助模型链、提示语和记忆索引。HTTP 路由的旧局部赋值不充当生产生效证据。
6. 等待两端 applying 回执，提交签名 committed 版本，再等待两端 committed 回执；然后才返回 HTTP 200。

回执绑定 revision、sequence、phase、原始摘要、有效身份、凭据版本摘要、releaseId、角色、PID、进程启动时间和系统 boot ID，并核对活动颜色、systemd MainPID、排空状态及新鲜度。旧进程、错误版本、过期或来自未来的回执不能通过。

## 准入与记忆索引

`applying`、`rolling_back`、`recovery_required` 不保留旧 consistent 假象，阻断新执行；观察器仍能应用配置并生成证据，避免恢复死锁。

模型页包含 memory.index，共享刷新器因此也准备、提交和回滚真实 MemoryIndexService。准备只解析凭据；整体成功后才退役旧 watcher，仍被在途请求引用的服务保留到停机。回滚恢复原服务，而不只改回 JSON。

仅模型路由注入独立受控生产发布器，不向普通接口设置 `allowProductionMutation: true`。其他配置接口保持各自现有生产限制。

## 失败与恢复

| 情况                                   | 行为                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------ |
| 版本冲突、确认缺失、候选非法           | 拒绝发布，不推进现有配置；版本冲突保留专用错误码                               |
| Worker 未生效、目标进程或颜色变化      | 不报告成功，恢复旧文件及两端运行态后重新读回                                   |
| 签名意图写入前后、配置替换前后进程退出 | 持久日志识别前后合法版本，活动 API 按原锁规则尝试恢复                          |
| 恢复时进程不可用                       | 保留 recovery_required，暂停新执行，不谎报回滚完成                             |
| 恢复发现事务外磁盘改写                 | 不覆盖未知写入，保留证据并拒绝放行                                             |
| 已持久提交但最终回执丢失               | 返回 HTTP 500 与 CONFIG_MUTATION_COMMITTED，要求重新读取，不按“未保存”盲目重试 |

恢复沿用现有诊断锁的死 PID / 120 秒 stale 规则，强杀后不保证立即恢复。进程无法启动、运行态恢复门持续为脏、Vault 不可用或存在未知磁盘内容时，需要先恢复运行条件，不能删日志、修改环境标识或接受 observed 来强行放行。

生产轮换保留旧 SecretRef，供在途运行与历史恢复使用。完全未提交或完整回滚的失败候选按现有错误契约清理；提交后或恢复不确定时，不撤销仍可能在用的凭据。本次未实现自动历史 Secret/快照回收，应作为受控运维保留策略处理。

## 发布、重启与回滚

相同 releaseId 使用签名在线 expected。代码版本变化时，目标代码使用自身解析器与发布环境计算 expected，同时验证磁盘属于签名快照；不把代码 A 的有效摘要冒充代码 B 的摘要。

生产状态采集、现场组件采集、离线恢复、Admin Runner 和旧实例回滚边界使用相同的身份选择规则；远端工具传输清单包含签名验证模块。

正常重启保留已提交在线版本。代码发布失败时，旧实例按可信在线版本而不是过期 `.release.env` 摘要恢复。回退代码仍通过受控制品发布与目标版本兼容性检查；不能解析当前配置的旧版本被拒绝，不丢弃合法配置以伪造回滚成功。

## 验证及适用边界

测试覆盖真实生产 HTTP 保存、Vault 轮换、两个独立运行态、真实子进程 Worker 重启与保存中途重启、错旧回执、并发保存、失败补偿、中断恢复、主机发布互斥、签名篡改、环境隔离、代码发布身份选择，以及前端生产确认、取消保留草稿、等待生效与错误语义。

机制沿用可信 root 与单主机部署边界，不声称抵御已控制 root 的攻击者，也不是多主机共识协议。成功保存证明配置持久化及两端应用，不保证之后所有上游供应商请求都成功。

最终测试数量、提交 SHA、CI 和构建结果以 PR #593 检查记录为准；生产部署及线上验收没有在本 PR 执行。

## 冷启动与中断回滚的恢复入口

API 与 Worker 在加载配置之前，只对原发布版本的已签名中断事务尝试恢复。拥有者仍存活的正常事务不被接管；两个 OS 互斥锁、候选/原版本字节校验和快照完整性必须全部成立，事务外磁盘改写绝不覆盖。恢复旧字节后保持 recovery_required，不会在启动辅助函数里提交成功。启动装配与业务准入分离，观察者能够完成初始化，但业务执行和就绪状态仍关闭，直到正常发布器重新收集 API、Worker 的对应版本回执。回滚先恢复旧字节再改写阶段目标，因此两种写入间崩溃也仍有完整的候选与原版本记录可供恢复。
