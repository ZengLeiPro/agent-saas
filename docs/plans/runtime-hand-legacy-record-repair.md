# 存量会话执行环境登记冲突修复方案

日期：2026-09-07

状态：代码修复和本地验证已完成，待 PR 审查与发布；生产存量数据尚未更新。执行步骤见 [存量修复操作说明](../runbooks/legacy-hand-repair.md)，部署风险见 [工作流审查](../reviews/deployment-workflow-audit-2026-09-07.md)。本文件不代表生产数据更新、部署或 Workflow 变更授权。

## 一、问题与根因

生产会话 `cb1a3ad4-8971-5b01-9252-1f0cac7bd7f6` 同时存在两条 ACS 执行环境登记：

- 旧版：`{sessionId}:agent-saas-acs`
- 新版：`th_{tenantHash}:{sessionId}:agent-saas-acs`

两条记录均为 `ready`，指向同一工作区和 Sandbox 范围。

当前路由要求只有一条就绪记录才能选择环境。重复记录导致路由返回 `none`，`WaitForWorkspaceReady` 随后将冲突误报为“准备中”，导致 Agent 无法继续使用工作区。

发布流程未覆盖“旧版本创建会话 → 升级 → 原会话续聊”的兼容性验证。

### 已核实证据

- 09:24:05：该会话 Sandbox `…bc7f0254` 初始化成功，登记为 `ready`。
- 09:24:49—09:28:01：连续 5 次 `WaitForWorkspaceReady` 返回 `provisioning`。
- 相同记录结构的本地复现：两条就绪记录返回 `none`，仅保留新版记录时返回 `ready`。
- 生产发布于 05:19 完成蓝绿交接，旧 Worker 于 05:19:42 排空退出；未发现早上故障由旧 Worker 持续存活造成的证据。
- 新 ID 格式在此前几个生产版本中已经存在，不能单独归因于当天凌晨最后一次发布。
- 后台会话详情仅按 `workspaceId` 筛选环境，会混入同一用户其他会话的 Sandbox。

以上时间均为北京时间。生产发布记录：https://github.com/ZengLeiPro/agent-saas/actions/runs/34060310070

## 二、修复目标

- 已有会话继续使用原工作区，文件和历史记录完整保留。
- 同一会话、同一执行环境提供方只有一个有效路由。
- 新旧登记记录能够安全接管，重复执行修复不会产生额外副作用。
- 区分启动中、启动失败和登记冲突，避免无限等待。
- 后台准确展示当前会话对应的执行环境。

## 三、处理原则

1. 登记记录退役与实际 Sandbox 删除分开处理。
2. 不直接将全部旧记录改为 `unhealthy` 或 `destroyed`。
3. 不按更新时间简单选取一条，不隐藏不同环境之间的真实冲突。
4. 不修改其他租户、用户或会话的登记记录。
5. 被执行中任务引用的旧记录，须等待任务结束或完成可验证的安全交接。
6. 存量修复必须先输出清单、保存变更前快照，再执行限定范围的更新。

## 四、代码修复

### 4.1 建立登记记录退役机制

优先采用明确的“已被替代”标记，例如：

```json
{
  "supersededBy": "新版 Hand ID",
  "supersededAt": "退役时间",
  "supersededReason": "tenant_hand_identity_upgrade"
}
```

字段名称和存储位置以现有模型评审结果为准。若采用独立状态，需同步更新状态类型及所有消费者。

退役记录必须：

- 不参与路由和就绪判断。
- 不被健康扫描、初始化重试或恢复任务重新激活。
- 保留审计信息和历史关联。
- 不因退役触发 Sandbox、工作区或文件删除。

### 4.2 实现新旧记录接管

在注册新版 Hand 前，查询当前租户、会话和提供方对应的新旧记录。

| 场景                             | 处理方式                                               |
| -------------------------------- | ------------------------------------------------------ |
| 仅存在新版记录                   | 沿用现有注册、恢复流程                                 |
| 仅存在旧版记录                   | 校验归属和环境身份，完成新版注册及就绪验证，再退役旧版 |
| 新旧记录并存且确认指向同一环境   | 校验新版可用、旧版无活跃引用后，退役旧版               |
| 新版尚未就绪                     | 保留旧版信息，按明确的接管流程推进，不能提前退役       |
| 新旧记录指向不同环境或归属不一致 | 停止自动接管，返回明确冲突                             |
| 旧版仍被执行中任务引用           | 延迟退役，待安全交接条件满足后重试                     |

接管需具备事务或条件更新保护：

- 以租户、会话、提供方作为并发协调范围。
- 更新前再次校验状态、版本及活跃引用。
- 防止多个 Worker 重复接管。
- 重复调用得到一致结果。
- 外部恢复请求不应占用长时间数据库事务；应通过持久化接管状态衔接。

### 4.3 修复路由与等待工具

涉及文件：

- `server/src/runtime/runtimeHandRegistration.ts`
- `server/src/runtime/handStore.ts`
- `server/src/agent/tenantRemoteHandSelection.ts`
- `server/src/agent/toolRuntime.ts`
- `server/src/runtime/handHealthScanner.ts`
- 其他会重新激活或清理 Hand 的消费者

统一规则：

- 路由排除已退役记录。
- 多条有效候选无法确定唯一环境时，返回明确冲突，例如 `RUNTIME_HAND_AMBIGUOUS`。
- `WaitForWorkspaceReady` 仅在确有初始化或恢复过程时返回 `provisioning`。
- 冲突时返回失败原因及可追踪标识，不再建议无限等待。
- 保持现有租户隔离和运行级隔离校验。

### 4.4 修复后台会话环境关联

涉及文件：`server/src/routes/platformObservability.ts`。

当前仅按 `workspaceId` 筛选，会展示同一用户其他会话的 Sandbox。

改为结合租户、会话和 `sandboxScopeId` 等权威字段关联。无法精确关联时明确提示，不推断为当前会话环境。

## 五、生产存量修复

### 5.1 只读盘点

输出待处理清单，至少包含：

- 租户、用户、会话 ID。
- 新旧 Hand ID、状态、创建和更新时间。
- 环境提供方、工作区、Sandbox 范围。
- 新版环境就绪证据。
- 旧记录活跃引用情况。
- 建议操作及不能自动处理的原因。

此前已发现当前租户有 3 个会话存在重复就绪记录，执行前必须重新查询，不能直接使用旧清单。

### 5.2 限定更新

在兼容代码上线后：

1. 保存获批清单和变更前快照。
2. 先修复指定故障会话。
3. 使用参数化 SQL、事务和状态条件更新旧记录的退役标记。
4. 校验实际影响行数，不符预期则回滚。
5. 验证通过后，再处理确认范围内的其他记录。

不删除历史登记、Sandbox、工作区或会话文件。

### 5.3 修复后读回

确认：

- 新旧历史记录均保留。
- 只有一个有效路由。
- 旧记录不会被扫描器重新激活。
- `WaitForWorkspaceReady` 返回 `ready`。
- 原会话能够在专用验证路径完成写入和读取。
- 暂停后续聊仍能恢复。
- 原业务文件未被修改。

## 六、验证要求

| 场景               | 验收结果                                   |
| ------------------ | ------------------------------------------ |
| 旧记录升级接管     | 新版可用后旧版退役，原文件保留             |
| 新旧两条均就绪     | 接管后唯一路由，等待工具返回就绪           |
| 不同环境记录冲突   | 明确报错，不自动合并                       |
| 跨租户或跨用户记录 | 拒绝接管与路由                             |
| 旧记录存在活跃引用 | 不提前退役                                 |
| 并发续聊或接管中断 | 不重复注册、不重复执行外部操作，可安全重试 |
| 健康扫描与重启恢复 | 不重新激活已退役记录                       |
| 暂停后原会话续聊   | 恢复成功，实际读写通过                     |
| 后台会话详情       | 不混入同用户其他会话的环境                 |

必须增加真实升级验证：

```text
旧版本创建会话并写入验证文件
→ 保留数据库与工作区
→ 部署新版本
→ 原会话继续执行
→ 检查唯一有效路由
→ 读取升级前文件
→ 完成新文件写入与读回
→ 暂停后再次续聊验证
```

测试数据应专门构造或去标识化，不直接复制生产业务数据到测试环境。

## 七、发布门禁补充

经确认后调整 Workflow：

- 涉及持久化身份或记录选择规则变化时，要求升级兼容性验证通过。
- 将存量重复有效记录检查纳入发布前评估及发布后读回。
- 发布结果分别报告组件健康、记录兼容性和原会话业务验收。
- 迁移确认不能仅凭版本身份和 API readiness 判定业务兼容。

## 八、回滚方案

- 存量更新前保存精确记录快照及修复批次。
- 数据回滚使用条件更新，避免覆盖修复后新产生的状态。
- 恢复旧记录参与路由前，必须保证新版不会同时参与，防止重新产生冲突。
- 应用回滚版本必须理解退役标记，或配套完成受控数据回滚。
- 保留当前工作区和 Sandbox，不通过删除重建实现回滚。

## 九、交付与授权边界

交付内容：

- 注册接管、路由、等待工具和后台关联修复。
- 支持只读预览、限定执行、快照及读回的存量修复脚本。
- 单元测试、数据库并发测试和真实升级验证报告。
- 生产修复清单、执行结果及回滚说明。

先完成本地实现和验证，编译通过后提交本地 Git commit。生产数据更新、远程推送、部署及 Workflow 修改或触发，均在获得明确授权后执行。
