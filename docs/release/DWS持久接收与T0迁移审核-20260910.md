# DWS 持久接收与 T0 迁移审核

## 结论

V47 是 expand-only 迁移：只新增 receiver owner、原始 inbox、迁移账本及索引，不删除/重命名既有对象，不回填存量账号，不自动启用新 writer。旧账号继续按 legacy reader 运行；只有平台管理员显式发起 T0 且取得旧 invocation 的 durable journal 终态证明后，单账号才切换到 `durable-v1`。

## 写入与兼容顺序

1. 先发布能识别 `legacy`、`handoff_pending`、`durable-v1` 的 reader 和 V47 表。
2. T0 `prepare` 只创建零游标、无 owner 的 registration 和 `planned` 账本，不改变旧账号。
3. `begin` 原子改为 `handoff_pending`、递增 revision 并撤销旧 runtime lease；legacy selector 立即排除该账号。
4. 请求旧 invocation 停止；只接受 exact invocation 下所有 operation 的签名 `stopped/not_started` journal 证明。
5. 激活事务再次校验账号 revision、registration 无 owner、游标为 0、state 为 registered，然后原子切换 `durable-v1`。
6. 新 consumer 先将原始帧落入 PG，再调用既有 message router；业务处理成功后标记 forwarded，只有连续无 pending 的 cursor 才允许 ACK。

任何阶段的未知证据都保留为 `blocked`。`planned` 以外的状态不可 abort，防止把已撤销的 legacy authority 悄悄恢复。

## 回滚边界

存在任何非 `aborted` 迁移时，管理端 rollback check 返回 `reader_capable_rollback_floor_required`。实际生产 floor 必须在 staging 把具体 release digest、RBAC 和 mixed-image 行为验收后写入发布证据；当前没有生产激活，因此 floor 为 `NOT_RUN`，不能臆造摘要。

## 数据库审核

- `v47DwsDurableReceiverMigration.ts`：expand；固定表名由受控 prefix 组合，无用户动态标识符。
- `migrations.ts` / `latestMigrations.ts`：仅把治理版本 46 提升为 47 并按序注册 V47。
- `durableDeliveryStore.ts`：运行期参数化 SQL；无启动 DDL。owner/account/migration 均在事务内 `FOR UPDATE`，revision/epoch 失败即拒绝。
- release postcondition 校验关键列类型/nullable、主外键/唯一约束及三个准入索引均存在且 valid/ready。

`agentDwsRuntime` 接入 durable gateway 后，保守依赖分析首次把 40 个既有 Agent、DWS、Hand 与 transport 运行期模块纳入历史基线闭包。逐文件比较最老登记基线到本提交的增删行及 SQL 字面量后，这些模块没有新增、删除或修改启动 DDL；已有 `handStore` / `workspaceHandTools` 审核分类继续保留，只为此前没有覆盖的基线补充 `no-schema-change`。该补充不授权任何通配路径，仍由两端文件 SHA-256 精确绑定；以后任一文件变化会再次要求审核。
