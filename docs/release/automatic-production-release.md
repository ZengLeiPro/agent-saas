# 自动生产发布

## 日常操作

在现有「生产环境发布」中使用默认 `operation=auto`，填写发布原因，其余字段保留默认或留空。无需查找、填写旧 RC 编号。这里的“最新”指本次请求发起前，可信 main 历史中已经完成 Staging 验收的最新**源码版本**，不是最大 RC 编号，也不是尚未验收的 main HEAD。

系统在持久化请求中固定业务源码、部署引擎、原始验收候选和原因。排队、重跑或 main 新增提交不会偷偷换目标。`promote`、`checkpoint-repair` 和两个 `web-recovery-*` 高级入口继续保留；脚本调用这些高级入口应显式指定 operation。

## 执行顺序

1. 完整读取不可变候选与证明快照，按 Git 祖先关系选择目标；不把分页截断、缺失历史或冲突快照当成“没有未完成事务”。
2. 如果最近一次完整发布之后只有一个可证明可恢复的未完成事务，系统自动接续它。复用既有主机锁、前缀核验、Staging/配置/有效期检查、组件跳过与故障恢复；不强杀旧任务，不重放未知工具副作用。
3. 已完成组件只有在字节与身份精确匹配时才被既有发布引擎跳过。恢复旧版本本身**不是**本次新版本发布成功。
4. 若当前目标的生产基线已不适用、使用过历史 checkpoint 或目标验收期限已过，则使用同一个固定业务源码生成一个新的 RC，完成实际 Staging 部署和验收。旧 RC、旧证据与其有效期均不改写。
5. 晋级目标候选。最后调用 checkpoint-only 路径重新观察全部生产组件并验证持久化 checkpoint；最终 Manifest 源码必须与原请求目标相同。只完成恢复、只有绿色子工作流、只有健康接口或仍有 checkpoint 维护警告，都不能作为最终成功。

## 源码与部署引擎

自动刷新时，Staging 用当前请求固定的部署引擎处理旧候选的固定业务源码。业务产物仍来自该源码对应的成功 main CI，继续验证原 CI run/attempt、产物摘要、合并记录、祖先关系及依赖契约；不会把当前引擎检出目录当成业务源码重新打包。

现有 Evidence Writer 按源码 SHA 保存的记录保持不可变。自动刷新会重新实时观察生产、重新计算分类与迁移计划，并生成同一 schema 的独立权威证据，通过同一次 Staging run 的精确 artifact ID 交给后续 job，同时归档到新 RC 和原有 Staging artifact。**自动刷新禁止退回历史 checkpoint**。普通手动 Staging 的 Writer 读取/复用策略不变。

新增 `staging-source-binding.json` 明确绑定源码、引擎、Staging run/attempt、新 RC/Manifest、完整权威证据摘要、父请求及子步骤登记。GitHub Staging Deployment payload 记录该证明摘要。生产预检重新 GET 父请求、子步骤及原运行记录，与原始 artifact 联合核验；只有这条明确委派路径允许 `Staging run.head_sha != Manifest.releaseSha`。普通发布依然要求二者相同，迁移、核心业务烟测、撤销、状态分页、过期与新 attempt 拒绝规则不变。

## 并发、重跑和取消

自动协调 job 使用 `production-auto-requests` 队列；所有实际生产发布和冷备操作 job 使用原 `production-runtime` 队列，并继续保留生产主机锁。这避免父协调器占着同一把锁等待子发布。所有队列保持 `cancel-in-progress:false` 与 `queue:max`。

父请求和每个子步骤在 `production-request` 环境下保存 GitHub Deployment **调度登记**，并非生产成功声明。登记先于派发，包含固定输入和摘要。派发使用原两个 workflow、明确 run-name 关联和返回 run ID；响应丢失后只查找相同关联的运行，不重复 POST。重新运行父请求会读取原登记，不重新选择目标。不要单独 Re-run 自动子任务。

自动子任务在获得环境凭据前和开始变更前验证父请求仍活动、attempt 一致、委派记录及全部输入一致。父请求取消后不再发起新阶段；已经开始变更的子任务不被协调器强行取消，保留其自己的安全收尾。实际生产环境审批不被绕过。协调器仅有仓库读取、Actions 调度和 Deployment 登记权限，不接收云端或 SSH 凭据。

## 明确停止的情况

存在多个未闭合事务、已变更事务被撤销、未知现场或副作用、恢复候选已过期、原 CI 产物不再可用、子运行失败、派发结果无法唯一确认、证据被改写/缺失、权限不足或请求后的部署引擎发生变化，都会有界停止。不会修改恢复期限、跳过安全门禁或要求操作者轮流猜旧 RC。修复阻塞后仍使用同一个 auto 入口；重跑必须遵守原持久化登记。

整个协调过程有 350 分钟内部预算和 360 分钟 job 上限；子操作继续执行自身更短的超时。超时不代表已经开始的远程操作没有发生。应查看本次请求的 `automatic-release-*` artifact 及关联子运行，而不是反复创建相同人工 promote。

## 验证范围

新增测试覆盖固定目标/源码顺序、旧事务识别、目标撤销、派发响应丢失、登记重读、禁止重复派发、父子取消/attempt/身份边界、刷新独立证据、最终目标与 checkpoint，以及调用真实生产 Bash 预检和严格迁移校验器的跨源码/引擎回归。外部 GitHub/云端 I/O 在回归中隔离。正式 PR CI 另行验证全仓契约与构建；CI 通过不等于已经实际执行生产自动发布。

本改造不合并代码、不触发生产部署，也不修改既有交接文档或长期失修的 Agent/Claude 指令文件。
