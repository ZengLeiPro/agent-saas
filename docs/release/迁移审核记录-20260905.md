## 审核机制与边界

`config/release-migration-reviews.json` 为逐文件审核事实源。每条记录绑定完整生产 SHA、基线文件 SHA-256、目标文件 SHA-256 和本说明/验证代码 SHA-256。文件新增或删除以一侧 null 明示。变更任一端内容或证据后审核失效，必须重新审核。依赖闭包和未审核文件仍执行原保守检查；contract 即使有记录也禁止进入 RC。

no-schema-change 仅说明该文件差异不引入启动迁移，不保证全部业务行为无变化。expand 记录只覆盖普通初始化调用链，不授权显式 contract。审核结论由本次代码审阅及 PostgreSQL 实测形成，不代表生产已迁移或人工观察已完成。

## 2026-09-05 晚修订：PR 允许已审核 expand；无 SQL 变化的依赖模块自动判 no-schema-change

本记录落地后当天实测暴露门禁自身的两处设计缺陷，已直接修正，本记录的逐文件结论与摘要绑定不变。

**一、PR 路径此前不允许任何 expand。** `scripts/release/migration-plan.test.mjs` 的「real repository closure uses the PR base or a deterministic target-only fallback」断言 `phase === 'none'`，等于任何 PR 只要带一条完全合规、已审核登记为 expand 的 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，Static checks 必红；而同一套审核记录按生产基线路径却能放行三条 expand，两条路径口径不一致。审核机制写明的边界是「contract 即使有记录也禁止进入 RC」，从未禁止 expand 进入 PR。现该断言改为 `ok === true` 且 `phase !== 'contract'`（`none`/`expand` 均可）。`.github/workflows/ci.yml` 的 Static checks 与 `scripts/release/check-reviewed-migrations.mjs` 只读 `createMigrationPlan` 的 `ok`，`promote-release.yml` 也只接受 `none:not_required|expand:required_after_observation`，无需另行改动。contract 阻断与 `!ok` 阻断保持不变。

**二、闭包过粗，非 SQL 改动被当迁移。** 被闭包纳入的依赖模块（不是 `MIGRATION_PATHS` 匹配的迁移根、也没有 expand 注释）只要有删除行就被要求「独立 contract release」，纯类型抽出（如 `server/src/data/transcripts/parse.ts` 的 87 行删除、零 SQL 变化）也要走人工审核——这正是本记录开头「原检查产生 153 条阻断，涉及 46 个文件」的成因。现在 `migration-plan.mjs` 在逐文件判定处增加一条自动 no-schema-change 判定，当且仅当同时满足：

1. 是脚本模块，且不是迁移根（`isMigrationPath` / `GOVERNANCE_MIGRATION_PROVIDER_PATH` 都不命中）；
2. 目标侧不含独立 `release-migration: expand` 注释；
3. 基线侧与目标侧的静态 SQL 字面量集合完全相同（对基线内容同样做一次提取后比较，含带插值模板的原始文本）；
4. 增删行文本经 `normalizeSqlForClassification` 后不匹配 `MIGRATION_PROVIDER_SQL_PATTERN` / `CONTRACT_PATTERN` / `DYNAMIC_SQL_PATTERN` / `UNKNOWN_SQL_PATTERN`；
5. 两侧变更行都没有触碰「import 时会执行代码」的顶层语句（否则 SQL 可以不经字面量落地）。

满足则该文件记为 `classification: 'no-schema-change'`，进入 inventory、不进 `blockingReasons`、也不把计划相位抬成 expand；任何一条不满足都退回原有严格逻辑。迁移根文件、含 SQL 字面量变化的文件、非脚本 SQL/JSON 资源和 contract 判定一律不放宽。
