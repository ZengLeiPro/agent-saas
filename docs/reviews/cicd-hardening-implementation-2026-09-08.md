## 发布行为

PR 运行按影响选择的检查、迁移审查、源码守卫，以及受影响的发布包和离线浏览器验证。`Build & Check` 聚合所有必要 job；意外 skipped、failure 或 canceled 都失败。完整覆盖率报告从核心门禁分离，覆盖率收集仍保留，缺少分片不会产出貌似完整的报告。

main CI 构建不含生产凭据的 Linux 包，使用 `release-packages-<sha>-<run>-<attempt>` 保存。Staging 先验证同 SHA、main push、APP CI workflow 和成功运行，再下载并验证 producer、锁文件、索引及每个文件的摘要/大小。ACS 镜像摘要在取得权威构建记录后绑定，包内容不重新构建。已有不可变 RC 沿用其原始字节。CI 只重跑失败 job 时，核对原成功构建 job 的具体 attempt 和上传结果后复用其产物；全量重跑优先最新成功包。七天过期则明确要求为原 SHA 重跑完整 CI。

Staging 的 Writer 升级和生产证据准备在在线槽锁外；部署与短业务验收在锁内。长时间外部 Agent 验收仍是独立可选任务，使用同一在线槽时必须持锁，避免中途换版本。GitHub 默认并发只保留一个 pending，本方案代表最新部署意图，不承诺每个 main SHA 自动发布。

生产正常模式维持所有严格检查。`recovery_mode=repair` 仅允许替换 App/Worker 的兼容 none/expand 候选，旧 App 可以不健康，但必须证明实际安装字节、活动路径、角色和配置与已提交身份一致；Web/ACS 仍需健康。候选启动、切流和最终读回不豁免。配置漂移、无法验证的安装、混合且未提交的 App 代际不能以 repair 猜测修复；应先按原发布重试/恢复记录处理。

最近成功 checkpoint 由完成发布后的新鲜严格读回产生，保存 Manifest、完成记录及完整组件身份；严格读回、五分钟新鲜度检查、身份核对和原子替换在同一主机发布锁内完成。用它准备修复 RC 时明确标记为历史基线，不传播历史健康或配置状态冒充当前观测。尚未建立 checkpoint 的旧环境继续失败关闭。

## 验收与边界

已经取得的局部证据包括：33/33 迁移分析等价；165 项原迁移测试及新增隔离测试；Writer 真包启动；业务短 smoke 反例；生产操作/ACS 排空和 PostgreSQL 后条件回归。真实 Linux 构建包多进程和 ACS 入口均已通过；受控并发的整套 Release/Staging 800 项合同全部通过，包括实际 PG16 后条件。

最终交付前还需完成最新代码的 Linux 发布包验证、全局合同/类型/静态检查、PR 必需检查及测试环境实发观察。线上速度改进以同类型 PR 和发布采样为准；本机迁移减少约 80% 不等于整条 CI 减少 80%。生产发布是否执行及其结果会记录在此处，不能以本地测试代替。
