## 2. 用户目标与必须保留的设计边界

用户要求的是组织持有的独立数字员工，首先完整做好钉钉：

- 员工有稳定身份、专属钉钉成员账号、自己的长期 workspace/NAS、设置、工具、技能和记忆。
- 每个群、每个私聊独立上下文，可继承总体配置并单独调整；私聊也由员工主体持有。
- 群有持续前台，内部可以有多个独立工作话题；群上下文持续性不等于共享所有任务 transcript。
- 复杂/执行工作交给子 Agent，前台可以继续交流、接补充和取消；结果由前台负责验收交付。
- 支持非 @ 续聊、有节制的主动参与、自动记忆整理和长期职责。
- 反馈自然、及时、准确；后台能够解释配置为何生效或不可用。
- 与普通用户共享基础功能服务，逐项支持 Agent principal；不能通过假人类用户维持表面兼容。

复用 OrgAgent、现有 binding/conversationSpaceId、WorkConversation、WorkOrder、BackgroundTask、inbox/outbox、租约/fence 和 NAS 隔离。不得通过删除权限校验、共享个人凭据、挂载整个员工目录给所有群任务、遇发送超时盲目重跑业务来修复。

候选新字段/组件名称、SLO、工期是设计建议。可依据当前代码选更合适的实现，但必须满足上述行为和验收。钉钉闭环包括主方案 A—K；L 的飞书/企微先保留适配边界，真实接入按用户后续范围执行。主方案 11.4 的业务模块对等需要独立列项，不能在只打通文档读取后宣布所有钉钉能力完成。

## 6. 实现、验证、联调、上线分别记账

每个工作包分别记录以下状态，不用单个“完成”覆盖全部：

1. **实现**：代码、schema、UI 和提示契约是否完整。
2. **本地验证**：回归、类型检查、真实 PG 组合、浏览器验证等应做项是否通过。
3. **环境联调**：实际测试账号、DWS、Worker/NAS 和外部结果是否通过。
4. **发布验收**：是否合并/部署、是否通过灰度与需要的长期运行验证。

允许记录“实现及本地验证完成，真实 DWS 联调待执行”，并继续独立工作。不能将待联调、跳过、无测试收集或命令未执行计为通过。跨七天试点未结束时，长期值守验收保持待验证，不能通过缩短运行时长得到“完整通过”。

所有证据附当前 SHA、命令、执行目录、运行时间、测试数/跳过数、结果和必要日志路径。身份、凭据、个人会话内容不得写入公开 PR 或可共享报告；使用脱敏 fixture。

测试按改动选择：相关回归 → 受影响 package 类型检查 → 必需的组合/界面/协议验证 → 仓库要求的提交和 PR 检查。当前 `package.json` 有 `preflight:pr`、ratchet 等命令，执行前检查脚本含义和当前要求。不要每次编辑都重跑整个仓库测试；也不能因原有单元测试全绿跳过新增关键组合场景。

改 shared 契约时检查实际消费者，必要时覆盖 web/mobile；改 Worker/Hand/workspace 协议时验证版本协商、旧任务恢复和混合版本滚动升级。数据库迁移须兼容旧行与进行中任务，提供回滚/暂停策略；生产执行另按已有授权处理。

## 7. 自主推进、多人协作与交付

- 在用户授权的实现范围内持续做代码、测试和修复，不为常规命名、目录拆分、兼容适配反复请求确认。
- 按能独立验证的改动拆分提交和 PR。授权创建/推送分支及草稿 PR 时直接执行；未获得相关授权时先把本地成果做成可审阅状态。合并、部署、真实外发、生产迁移是否执行以用户实际授权为准；已有授权无需再次询问。
- 遇到外部账号、真实收发或生产状态边界，先准备具体变更、测试方案、目标对象和回滚，再就缺少的那一项提出最小问题，继续其他不依赖它的工作。
- 可并行的具体子任务主动委派。第一批适合拆成 Context 授权、消息恢复、配置继承；跨模块共同字段由一个主 Agent 维护。子 Agent 不能各自创建互不兼容的身份/配置体系。
- 每个关键改动完成后让未参与实现的 Agent 独立审阅，关注真实调用链、权限阴性场景、恢复状态和兼容性。修复有效发现，运行相应回归；无新变化时不要无止境重复审阅。
- 不用修改测试期望或删除保护来掩盖行为回退，不顺手进行全仓重构、清理或依赖大升级。
- 每个可评审工作包结束、开始下一包或发生阻塞时更新第 8 节。最终答复必须独立包含已做内容、验证、已知限制、未完成项、分支/PR 和文档入口，不能只说“见 Todo”。
