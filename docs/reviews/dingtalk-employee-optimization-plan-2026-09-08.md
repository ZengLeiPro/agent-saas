# 企业专家与钉钉员工优化研究方案

研究日期：2026-09-08。代码基线：`main`，`c73689eab0f4a119f8efc1c5e0f8f8092493f33c`。

本报告基于当前代码、三个并行专项审计、现有针对性测试、实际函数最小复现和官方文档。没有修改产品代码，没有连接生产数据库或查询生产日志，没有向钉钉发送消息。因此，“确定缺陷”指当前代码可证明的组合行为；不表示已将用户遭遇的每一次线上异常追溯到该原因。性能数字和工期是后续建议目标，不是本轮实测。

## 0. 新对话实施入口

准备让新 Agent 实际迭代时，先读[执行交接](dingtalk-employee-execution-handoff-2026-09-08.md)，再读本方案，并按工作包查[配套证据](dingtalk-employee-optimization-evidence-2026-09-08.md)。执行交接补充了首批动作、A/C 依赖、贯穿各阶段的 K 子项、验收层级、未跟踪文档带入 worktree 的方法、进度记录和可复制的启动提示语。

本方案保持研究基线，实施状态以执行交接的进度记录和实际代码为准。第 12 节中的提示语是产品运行提示的示例，不能代替新对话的实施指令。发现代码已变化时只复核有关结论，不必从头重做整份研究；完成一个阶段后继续推进已授权的后续工作，不能把局部修复当成整个目标完成。

## 结论与建议决策

建议把现有企业专家升级为**组织持有、可长期运行的数字员工**：钉钉只是它的一个工作入口，群聊和私聊是它工作的不同场所，任务是它委派给执行 Agent 的工作单元。员工身份、长期文件、设置、记忆和工作职责具有独立生命周期，不能随某个人类请求者的账号、某个聊天 session 或某个执行容器而消失。

现有代码已具备独立 Agent workspace、专属 DWS 账号、群策略、后台 Worker、持久化任务和消息投递等基础，值得保留。当前的主要障碍是这些模块之间没有形成一致契约：群与私聊使用不同主体；配置在前台、Worker 和长期 session 中有不同版本；工具在配置中允许却没有合法执行层；错误恢复缺少闭环；数据同步、记忆整理、主动参与被混为一谈。

优先级应为：

1. 修复已确认的执行能力断路、配置不生效和消息恢复问题。
2. 统一员工主体、群与私聊的会话模型、配置发布和上下文继承。
3. 接通普通群消息，先保证自然续聊，再开放有节制的主动参与。
4. 补齐员工自己的记忆整理、长期职责、后台管理和运行可观测性。
5. 以同一套会话与执行内核接入飞书、企微。

不需要重写整套 Agent runtime。应在现有 OrgAgent、binding 的 conversationSpaceId 边界、WorkConversation、WorkOrder、BackgroundTask 和 DeliveryIntent 上逐步收敛。

## 1. 官方 Claude Tag 的实际机制与可借鉴之处

用户提到的名称是准确的：Anthropic 有官方 **Claude Tag**。其发布说明将它定位为团队中的协作成员，支持共享工作、积累上下文、主动跟进和异步执行；当前产品主要在 Slack 中使用。[官方发布说明](https://www.anthropic.com/news/introducing-claude-tag)

这与 Claude Code Channels 有联系但不是同一能力。Channels 是外部消息进入运行中会话的桥梁；Tag 同时包含组织身份、频道配置、记忆、任务和主动参与的产品设计。本方案以 Tag 为主要对标，Channels 和子 Agent 文档只作为局部机制参考。[Channels](https://code.claude.com/docs/en/channels)

| 观察到的官方机制                                       | 对本项目的启示                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------- |
| 频道有自己的会话，需要调查或执行的工作进入线程工作会话 | 同群持续上下文与任务独立上下文可以同时成立，不能在二者之间二选一 |
| 线程中的多人可以继续推动同一项工作                     | 请求者是参与人和授权来源，不应成为共享任务的唯一所有者           |
| 无 @ 消息可以被忽略、短答、启动工作或转交已有工作      | 增加“是否应当参与”的决策层，而不是给所有群消息运行完整执行 Agent |
| 长期工作可配置为 routine                               | 定时职责应是持久化业务对象，不能只依靠当前模型自己等待           |
| 按频道和工作区管理记忆                                 | 员工有统一身份，不代表不同群和私聊可以混读所有记忆               |
| 组织为 Agent 配置外部工具身份                          | 管理员负责配置，但运行时使用员工自己的授权和资源范围             |

频道与线程模型来源：[How Claude Tag works](https://claude.com/docs/claude-tag/concepts/how-it-works)。主动参与来源：[Control when Claude Tag responds](https://claude.com/docs/claude-tag/users/when-claude-responds)。长期职责来源：[Set up routines](https://claude.com/docs/claude-tag/users/proactivity)。

官方在 2026-08-13 说明，主动参与应结合频道整体上下文、记忆和常驻指令判断，而非只看当前一句话。这直接支持本项目增加频道上下文管理和相关性决策的方向。[官方主动参与更新](https://claude.com/blog/claude-tag-now-reads-even-more-of-the-room)

有两点应按本项目需求另行设计：官方 Tag 的私聊执行仍使用个人账号的能力；用户要求我们的私聊也由员工独立持有。官方公共频道可以共享工作区记忆；本项目不能据此把所有钉钉群自动视为公共群，应使用显式的数据可见范围。[Tag 账号与入口说明](https://support.claude.com/en/articles/15594475-what-is-claude-tag)、[Tag 记忆说明](https://claude.com/docs/claude-tag/users/memory)

## 2. 钉钉、飞书与企微的能力边界

### 2.1 钉钉有官方的不依赖 @ 的接入路径

普通应用机器人的消息接收与 DWS 的个人成员身份事件是两套能力。普通机器人的群接收文档说明主要通过 @ 触发；不能将这一边界套到 DWS 成员账号。[钉钉机器人接收消息](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/appbot/receive/)

本仓库 `Dockerfile:93` 固定 `DWS_CLI_VERSION=1.0.60`。对应官方版本的事件文档列出：

- `user_im_message_receive_at`：被 @。
- `user_im_message_receive_o2o_all`：全部私聊消息。
- `user_im_message_receive_group`：指定群消息。
- `user_im_message_receive_group_all`：全部群消息。
- 消息撤回、表情回应、成员加入退出和群解散等事件。

依据：[DWS v1.0.60 IM 事件目录](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/v1.0.60/skills/multi/dingtalk-event/references/event-im-keys.md)。这些能力支持本项目的技术方向，但本轮未在实际员工授权账号上验证订阅权限、跨组织范围、配额或消息重放保证。

建议以已启用群的实时事件作为主链路；授权范围较广的员工可以配置账号级全群事件，在应用侧按会话策略分流。先验证实际 CLI 的 `--help`、事件 schema、组织授权和消费语义，固定适配器契约，不在运行时盲目跟随最新版命令。历史消息拉取用于上下文补齐或断线对账，不能成为实时收件的主要实现。

“任何群”在产品上的可兑现含义应是：员工账号已加入、平台允许访问且符合组织策略的群，均可自动建立自己的会话配置并继承默认值。用户无需为每个群手填一组内部 ID。账号无法访问的群不会因为增加一个配置开关就变得可访问。

员工的钉钉账号必须是组织为该员工持有的专用身份。账号创建、加入企业、登录验证及钉钉侧授权仍按平台流程完成；本轮没有验证“自动注册一个普通钉钉账号”的能力。平台负责账号绑定、托管、健康检查、换绑和生命周期，不借用当前管理员的私人钉钉登录态。

### 2.2 其他平台先保留适配接口

飞书官方资料已说明，接收群内非 @ 消息涉及群消息权限，例如 `im:message.group_msg`。后续应独立验证应用类型与权限，复用本项目会话和任务内核。[飞书官方插件说明](https://www.feishu.cn/content/article/7613711414611463386)

企微的智能机器人、企业应用和其他接入类型需分别验证。本轮官方接收消息页未能成功读取，故不承诺“企微任意群全量读取”或“普通成员账号托管”已具备与钉钉相同的支持。企微接入应单独做能力验证，不能把群 webhook 当成完整聊天员工。

适配器至少声明：群/私聊接收、非 @ 消息、历史补齐、线程/引用、主动发送、消息编辑/撤回、附件、回执、幂等、速率限制。界面只开放已经验证可用的模式。

## 4. 确定缺陷与优先级

以下定位相对于本报告代码 SHA。源码路径及行号便于后续实现前复查。

### F01：群 Worker 无法使用已配置的钉钉业务工具，P0

群启用要求 `dispatcher`（`server/src/routes/agentDwsAccounts.ts:306`）。dispatcher 工具白名单没有 `DwsBusiness`（`server/src/runtime/dispatcherMode.ts:11`）。而业务策略对 `executionRole === 'worker'` 无条件拒绝（`server/src/dws/sharedGroupBusinessPolicy.ts:61`）。

因此前台不能做、被要求接手的 Worker 也不能做。配置 DwsBusiness 和资源白名单不能改变这一事实。这是能力接线问题，不能靠提示模型“多使用工具”解决。

修复：在 Worker 中开放经过资源、操作、身份与授权检查的 DWS broker；前台继续承担接单和沟通。不要直接把员工完整 DWS 凭据和全部可访问数据暴露给所有任务。

### F02：合法任务 workspace 被组织 Context 检索拒绝，P0

任务 workspace 合法派生为 `agentWorkspaceId__task_<digest>`（`server/src/runtime/orgAgentTaskWorkspace.ts:69`），但 Context 检索要求 workspace ID 与 Agent principal 的主 workspace 完全相等（`server/src/agent/contextSearchToolProvider.ts:215`）。

本轮已用实际导出函数和真实任务 workspace 派生函数做最小复现：前台主体解析成功，Worker 抛出 `CONTEXT_RECALL_SUBJECT_MISMATCH`。dispatcher 同时不能调用 ContextSearch，所以相关群的组织知识检索没有正常执行层。

修复：显式验证受信任的 `employee principal → task workspace → current attempt` 归属关系，保留租户、Agent、群范围和事实源校验。不能简单删除检查，也不能仅凭字符串前缀判断归属。

### F03：群指令与记忆没有确定性下传到 Worker，P0

群指令和当前治理记忆被组装进前台的 `channelContext.systemContext`（`server/src/dws/personalMessageRouterHelpers.ts:45`）。后台重建 channelContext 时没有携带这个文本（`server/src/runtime/background/backgroundTaskService.ts:549`），请求使用模型生成的 `metadata.prompt`（同文件 `:578`），Worker 指令来自全局 `orgAgentSnapshot.instructions`（`server/src/runtime/subagent/subagentRunner.ts:507`）。

能力白名单和技能过滤有硬继承，指令和记忆则依赖前台模型是否主动转述，二者不可混为一谈。

修复：委派时生成结构化、持久化的工作上下文包，包含合成指令、会话相关摘要、记忆引用、资源范围、配置 revision、任务目标及验收标准。运行时注入系统约束，不让模型负责复制权限或重要工作规则。

### F04：配置接受 20,000 字符，实际群提示截到 8,000，P1

群 schema 允许 20,000（`server/src/routes/agentDwsGroupWorkspaceSchemas.ts:34`），提示组装只保留前 8,000，且 `bounded()` 折叠所有空白（`server/src/dws/personalMessageRouterHelpers.ts:52,165`）。

影响：保存成功不等于全部生效；后半段流程和格式要求可能消失，列表/代码结构也会被破坏。修复应统一预算、保留结构、明确告知超额，长资料改为被引用的文件或知识源；后台提供实际合成结果预览。

### F05：同一长期会话前台与新 Worker 可能使用不同配置版本，P1

session 初建时保存 OrgAgent snapshot（`server/src/runtime/orgAgentSessionResolution.ts:44`、`server/src/runtime/sessionCatalog.ts:32`）；前台后续运行会解析当前 OrgAgent（`server/src/runtime/rawRuntimeRunDispatch.ts:914,1225`），后台从任务/session snapshot 解析技能、指令与模型（`server/src/runtime/background/backgroundTaskService.ts:528`）。

这会形成“刚修改了总体指令，前台知道，执行者仍使用旧版本”的路径。修复时应明确：新回合使用哪个配置，新任务固定哪个版本，旧任务恢复如何兼容；权限撤销则始终实时优先。

### F06：unknown 投递核对为未发送后，不能重新被消费者领取，P0

状态链：发送结果 unknown → `markReplyUnknown()` 把关联 inbox 标为 dead_letter → 人工 `confirmed_not_sent` 只把 delivery 变为 pending → delivery consumer 排除 inbox 为 dead_letter 的记录 → inbox consumer 也不取 dead_letter。

证据：`server/src/dws/orgAgentVisibleReply.ts:52`；`server/src/data/agentDwsMessages/store.ts:554`；`server/src/data/orgGroupAgents/deliveryClaims.ts:166,299`；`server/src/routes/agentDwsAccounts.ts:353`。

修复必须原子协调两个状态机，确定由哪一侧继续投递；使用原正文和原幂等键，不重新执行已完成的业务。首回与最终结果是不同投递阶段，恢复不能仅补出“收到”而遗失最终答案。

### F07：私聊 unknown 没有对等的核对入口，P1

私聊创建的 delivery 无群 `bindingId`（`server/src/dws/orgAgentVisibleReply.ts:193`），唯一核对路由又必须找到群 binding（`server/src/routes/agentDwsAccounts.ts:366`），结果为 404。

修复：恢复接口升级为通用会话投递接口，以员工账号身份、会话、接收者和当前授权验证；群策略作为群场景的附加约束。

### F08：执行重试耗尽后没有可靠的用户可见终态，P1

router 异常路径主要记 fail 和日志，达到上限进入 dead_letter（`server/src/dws/personalMessageRouter.ts:350`、`server/src/data/agentDwsMessages/store.ts:572`），没有在该路径创建可靠失败通知。

影响：用户可能只看到“完成后会回复”，随后一直沉默。修复应区分“工作结束”和“用户已收到结论”，为已接单请求建立完成、失败、取消、等待输入的最终通知。

### F09：账号换绑提示与数据约束矛盾，P1

迁移保留 `UNIQUE(tenant_id,agent_id)`（`server/src/data/governance-schema/agentDwsMigrations.ts:49`）；旧身份群绑定被拒绝时提示为当前成员新建账号配置（`server/src/routes/agentDwsAccounts.ts:222`），但同 Agent 不能新建第二个账号，缺少对应替换流程。

修复：提供保留旧历史的换绑操作与身份 epoch；新旧身份的消息、订阅、配置和投递明确分代。是否支持同平台多账号是后续产品选择，当前至少应允许合法换绑。

### F10：知识技能和普通技能的群配置可选范围不一致，P1

全局运行技能包含 `allowedSkills + allowedKnowledge`（`server/src/data/orgAgents/runtimePolicy.ts:337`）；群 UI 只列发布的 skillIds（`web/src/components/AgentDwsAccounts/GroupAgentWorkspacePanel.tsx:525`），激活又只接受 `allowedSkills`（`server/src/routes/agentDwsAccounts.ts:312`）。

修复：从同一发布能力目录派生可选项、校验和 Worker 实际工具包，避免一个能力在总体配置中有效、在群里不可选或保存被拒。

## 5. 产品机制差距，不应误称为单点 bug

1. **线程独立合理，但群缺少持续前台。** 当前 active 群无法确定既有话题时，以引用 ID、messageId 或 eventId 建立 WorkConversation（`server/src/dws/orgAgentSharedGroupContext.ts:180`）。正确方向是“每群一个长期交互边界，内部多个任务线程”，而不是把所有工作塞进一个无限增长的大 session。
2. **群与私聊主体不同。** shared 群以 Agent 为 owner；私聊及 shadow 群仍用 requester binding（`personalMessageRouter.ts:575,898`）。这与用户要求的全渠道员工独立性不同。
3. **主动参与尚未开放。** 当前 event enum 仅 `at_me | all_direct`，保存 proactive 或关闭 requireMention 明确返回 400（`shared/src/types/agentDwsAccount.ts:14`、`agentDwsAccounts.ts:273`）。这是当前明确的能力限制。
4. **“三秒首回”计时不覆盖完整等待。** 身份目录、权限、群解析、会话绑定完成后才开始计时，私聊没有同样兜底（`personalMessageRouter.ts:480` 至 `:605`）；目录远程调用 timeout 可达 60 秒（`requesterIdentityResolver.ts:201`）。
5. **轮询已有，但含义不同。** DWS Context 每分钟 tick、群消息约两分钟同步、会议和知识库按更长周期同步（`context/sync/dwsContextRuntime.ts:38`）。它更新知识源，不会生成员工发言任务。普通用户 memory_poll 与企业治理记忆又是另外两套能力。
6. **提示语存在冲突。** dispatcher 要求播报任务短号和 queued/running（`dispatcherMode.ts:45`），群提示又要求没有歧义时隐藏内部短号（`personalMessageRouterHelpers.ts:59`）。这会带来不稳定的任务系统话术。

## 6. 目标产品模型与数据归属

### 6.1 员工是独立主体

沿用 OrgAgent 作为员工实体，不另建一套几乎相同的 Employee 数据体系。明确分离五种身份：

- **员工主体**：谁拥有设置、记忆、文件、任务和外部账号。
- **请求者**：本次是谁要求做事，具有哪些操作权限。
- **参与者/接收者**：哪些人能看到群内容、任务与结果。
- **管理员/维护者**：谁可以设置或停用员工。
- **外部凭据主体**：调用钉钉、知识库等系统时到底使用谁的身份。

管理员离职、请求者离线、session 压缩、Worker 重启都不应改变员工主体。请求者失去权限后，其私人结果可见性及未完成授权需要重新检查，但不能因此删除整个员工。

### 6.2 对现有实体做最小扩展

| 实体                | 建议职责                                                 | 复用方向                                                                                   |
| ------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| OrgAgent            | 员工身份、职责、全局能力、生命周期、预算                 | 继续使用现有主实体                                                                         |
| ChannelAccount      | 平台账号、组织、external user、profile、身份 epoch、健康 | 从 AgentDwsAccount 抽象接口，钉钉表可先保留                                                |
| ChannelBinding      | 一个员工与一个群/私聊的绑定及覆盖配置                    | 扩充当前群 binding，支持 direct                                                            |
| ConversationSpace   | 永久聊天边界、近期事件、摘要、记忆与参与策略             | 沿用 binding 现有 conversationSpaceId 边界与 serviceSessionId 字段，补齐持续前台和聚合状态 |
| WorkConversation    | 可并行的任务话题和工作上下文                             | 保留任务独立性，不再承担全部群聊天语义                                                     |
| WorkOrder / Attempt | 工作目标、执行状态、输入修订、产物、验收                 | 复用现有任务账本                                                                           |
| MemoryRecord        | 来源、scope、事实、权限、版本、纠正/失效                 | 复用治理记忆并接自动整理服务                                                               |
| Routine             | 员工长期职责、触发方式、下次时间、去重和停止条件         | 复用现有 durable scheduler 的底层能力                                                      |
| DeliveryIntent      | 要向谁发送哪个版本的哪条消息及确定性回执                 | 保留并修复群/私聊一致恢复                                                                  |

会话的稳定标识应覆盖 `tenantId + agentId + provider + channelAccountId + identityEpoch + externalConversationId`。不同平台、人类同名、群改名不得造成误合并。私聊缺少稳定 conversation ID 时，适配器可以使用经过验证的 peer ID 构造稳定键。

### 6.3 NAS 与执行容器生命周期分离

在现有员工根路径中逐步整理出逻辑区域：

```text
employee-root/
  profile/           # 员工总体设置的受控导出
  memory/            # 员工级公开记忆及索引视图
  conversations/
    <space-id>/      # 群或私聊专属资料与记忆视图
  work/
    <task-id>/
      attempt-<n>/   # 任务执行与产物
  shared/            # 明确授权共享给任务的资料视图
  skills/            # 员工私有技能和版本信息
```

这是逻辑结构建议，不要求一次迁移现有目录，也不改变 `.ky-agent` 等既有命名规范。PG 中的任务、配置发布和记忆记录仍有各自权威来源；NAS 是长期文件与可管理内容的存储，不能变成第二份未经同步的配置真相。

保留现有 connector workspace 隔离。任务只挂载自己的可写目录及明确授权的只读资料。员工总体 workspace 可以持久保存，但不意味着某个群的任务可以扫描其他私聊的文件。

验收：删除/重建执行 sandbox 不丢设置或成果；员工暂停后仍可查看文件；账号换绑不抹除历史；归档有可恢复记录；文件分享生成与接收者权限一致的入口。

## 7. 会话连续性、线程路由与上下文组装

一个群/私聊对应一个长期 ConversationSpace。它维护近期消息、参与者、常驻指令、简要工作状态和相关记忆。前台每次只加载足够的上下文，可压缩、换 run、换模型，不要求一个模型进程永远驻留。

当请求需要工具、调查或较长执行时，创建或继续 WorkConversation/WorkOrder，后台 Worker 独立运行。群 A 的任务不会占据群 B 的前台响应槽。

建议路由次序：

1. 原生 thread/reply 引用和当前消息的确定引用。
2. 明确指定的现有任务。
3. 对当前已知工作的高置信度补充，例如“刚才那份报价再加上华东区”。
4. 新任务或普通聊天。
5. 存在多个可能目标且会影响修改/取消/发送时，只问一个简短澄清问题。

语义路由只能选择候选任务，不能改变任务权限。消息与所指任务必须处于允许的会话边界；跨群共享任务只能通过显式授权的关联，而不是 embedding 相似度。

群近期事实与任务执行 transcript 分开维护。组装顺序建议为：组织约束 → 员工职责 → 当前会话指令 → 会话摘要 → 相关记忆 → 当前活跃任务 → 最近消息 → 本轮请求。工具返回、聊天消息和外部文档不能伪装成高优先级配置。

前台和 Worker 共用一个 ContextPacket 编译器，记录来源和截断策略；每一项不可丢失的行为规则必须确定性传递。Worker 不需要全群所有历史，但必须获得当前任务所需的规则、证据和结果投递边界。

## 8. 总体与个性化配置：继承、发布、解释

配置应支持组织默认、员工总体、渠道默认、具体群/私聊四层。不要把所有字段都做同一种 JSON merge：

| 配置种类                   | 合成方式                                                   |
| -------------------------- | ---------------------------------------------------------- |
| 安全和组织政策             | 上级约束不可被下级扩大                                     |
| 工具、数据、连接器权限     | 上级授权上限与本地选择取交集                               |
| 技能与知识                 | 同一发布能力目录，明确依赖；缺依赖时阻止发布               |
| 角色职责、常驻工作说明     | 按确定顺序分段组合，保留来源和结构                         |
| 语言、称呼、回复长度等偏好 | 最近一级显式配置覆盖继承值                                 |
| 主动参与与长期职责         | 受组织允许范围限制，会话可收窄；单独显示开关和实际生效状态 |
| 模型、并发与预算           | 员工/会话可设默认，受组织资源上限约束                      |

后台要回答“现在究竟用了什么配置”，而不只是提供编辑框。每个字段显示继承来源、覆盖值、最终值；能预览前台和 Worker 的有效指令、技能、工具与知识源；发布前执行可达性检查。

把当前多个独立开关组合为一份就绪检查：账号已授权、订阅工作中、员工已发布、前台可委派、Worker 协议兼容、至少一个实际工作能力可用、结果可以投递。无法启用时直接显示缺什么及修复入口。

配置生效规则建议：

- 新回合使用已发布的当前配置。
- 新建工作单将该回合的完整工作配置固定为版本化快照。
- 任务恢复使用原工作配置保持一致；权限、身份吊销和会话禁用始终重新实时检查。
- 在途任务切换业务指令必须作为明确的任务修订，有记录和结果提示。
- 风格变更不应无解释地把全部在途结果投递变为失效；重新做当前可见性检查后按明确策略继续或终结。

## 9. 子 Agent 与前台响应机制

### 9.1 继续使用前台调度器，但修复执行边界

前台负责理解、澄清、路由、委派、查进度、接收补充、暂停取消和验收结果。Worker 负责查询、分析、文件、代码和业务执行。当前 dispatcher 的硬工具边界值得保留，先让合法业务工具在 Worker 可用。

前台可以直接回答问候、身份、已有事实和已有任务状态。凡涉及新的工具查询、长文本研究、多步骤产物或业务修改，都快速委派。先保持明确边界，后续有评测证据时再允许极短、无工具的已知事实回答，避免为每个简单追问都建立无意义的重任务。

复杂任务可以由前台同时派出多个独立 Worker，如资料检索、数据分析和独立校验。首期无需开放无限递归子 Agent；Worker 需要更多帮手时提交结构化请求给协调者，由协调者决定。这样满足必须能委派的需求，同时保持任务和成本可追踪。

### 9.2 每次委派必须包含完整任务契约

至少包括：目标、输入与资料引用、交付物、验收标准、员工主体、请求者、会话范围、能力权限、配置版本、记忆引用、父任务、取消 token、deadline、预算和工作目录。无完整 scope 的任务不能进入队列。

不能用“子 Agent 继承前台能看见的工具”作为唯一规则：前台本来就不需要业务执行工具。应从员工与会话发布的执行能力上限派生 Worker 工具集，再叠加任务进一步收窄。

### 9.3 消息控制与执行队列解耦

暂停、取消、追加条件和查询进度必须通过可授权的控制路径快速到达协调者，不能排在被取消的长任务之后。同一前台会话串行修改状态，任务执行可并行。避免为加速而允许两个模型同时修改同一前台 transcript。

Worker 通过持久化事件上报阶段结果、输入请求、授权请求、完成和失败；前台根据事件唤醒，负责合并反馈。Worker 等待人类回答时保存 checkpoint 并释放执行槽，而不是在后台死等。

### 9.4 验收不能省略

Worker completed 不等于请求完成。前台必须检查产物存在、请求范围满足、来源可追溯、未完成项可解释；需要独立验证的任务再派校验 Worker。可直接可靠投递的已验证简单结果不必强行再调用大模型润色。

## 10. 主动参与与长期职责

应区分三个循环：

1. **收件循环**：实时事件到来，可靠落盘，更新会话日志。
2. **工作循环**：任务事件、用户补充、期限和例行职责触发工作。
3. **记忆循环**：把有价值的已发生事实整理成有范围、可纠正的记忆。

它们都属于员工，但不能混为一个每隔几秒给模型发送“看看有没有事”的大循环。

### 10.1 主动参与模式

| 模式     | 预期行为                                                  |
| -------- | --------------------------------------------------------- |
| 仅点名   | @ 时回答；其他信息是否保留按读取策略决定                  |
| 自然续聊 | 在已参与工作里接收后续补充，不要求每次再 @                |
| 相关参与 | 未 @ 但与职责、已有问题、明确请求相关时简短回应或转交工作 |
| 主动值守 | 同时执行明确的长期职责、期限跟进和事件订阅                |

首次上线建议先开自然续聊。主动参与先在不发言的观察模式运行，记录它原本准备何时说什么，由管理员评价后分群启用。发布成熟后，可由组织设置新群自动继承相关参与模式，减少逐群配置负担。

### 10.2 发言决策

确定规则先过滤重复、自己发送、无权限、静默、已回答、明显无关事件；合并短时间连发，再把近期会话、职责、未结任务和相关记忆给轻量决策。

决策输出至少支持：不回应、只更新上下文、直接短答、转交已有任务、新建工作、需要澄清。每个决策保留原因码、输入范围和配置版本。权限判定在模型之外，模型只判断相关性和行动价值。

适合插话：自己负责的问题出现新资料、有人提出职责内明确需求、已承诺任务到期、发现会影响当前工作的关键事实。通常不插话：闲聊、别人已回答、只是说“谢谢”、同样提醒刚发过、职责不相关、另一个员工正在答复同一件事。

发送前再核对最新会话：模型决定发言之后，可能已有真人回答或有人要求停止。过期建议应取消或合并，而不是照样发送。

### 10.3 长期职责

Routine 记录员工 owner、会话、触发条件、时区、执行窗口、相关源、权限版本、去重键、预算、停止条件和下次执行时间。用户可以自然地说“以后每天早上检查这里未解决的问题”，系统形成可查看、可修改、可暂停的职责。

有价值才打扰。例行检查未发现变化可以不发消息，但后台保留“已检查，无需通知”的运行记录。任务完成回报应走事件驱动，不要等下一轮定时检查。

重复提醒按未决事项而非按每次运行去重；“提醒一次”“仅工作日”“超过期限再提醒”“已经确认就停止”都应是明确规则。

### 10.4 断线恢复

优先使用官方事件能力。需核实 DWS ack/replay 语义；若无法保证应用落盘前的重放，建立持久化消费水位、断连记录及限定范围的历史对账。补齐消息保留原事件时间，不把两天前的普通闲聊当作刚发生的新请求自动回答。

## 11. 员工记忆与普通用户能力复用

### 11.1 分层记忆

| 层级            | 保存内容                               | 可见范围                     |
| --------------- | -------------------------------------- | ---------------------------- |
| 组织知识        | 公共规则、已授权资料                   | 由组织授权决定               |
| 员工总体记忆    | 员工职责、通用工作习惯、明确可共享经验 | 该员工获准使用的会话         |
| 群记忆          | 群决策、术语、偏好、项目背景           | 当前群，或明确允许的共享范围 |
| 私聊记忆        | 与该参与者的工作偏好和专属事项         | 当前私聊及被明确授权的任务   |
| 任务 checkpoint | 当前进度、证据、未决问题和恢复信息     | 当前任务及协调者             |

来自私聊或受限群的内容不能直接写进无 scope 的员工总体 MEMORY.md。无范围的共享文件会绕过检索层限制。跨范围晋升必须保留来源，并确认目标接收范围允许看到这些事实。

### 11.2 自动整理流程

以“新事实积累、任务完成、会话空闲、周期检查”触发候选抽取。抽取后检查来源、重复、冲突、有效期和可见范围，再写 MemoryRecord。个人偏好保存在当前会话，事实变化使用版本/替代关系，不把旧结论当作永久规则。

每条记忆保留 source message/task、scope、创建与更新时间、事实/偏好/指令类型、置信度和状态。管理员可以查看、纠正、删除、撤回晋升；用户在会话中询问“你记住了什么”只展示该会话允许看到的内容。

当前注入会取最新 20 条 Agent 记忆和当前工作话题的最新 20 条记忆，再做总长截断；它并非完整的群级相关记忆检索（`server/src/dws/orgAgentSharedGroupContext.ts:222`）。应升级为按任务相关性检索和预算分配，确保来源与规则不会在字符串尾部被无声裁掉。

### 11.3 与普通用户共享服务，不伪造人类账号

将需要 ownership 的底层服务接受统一 principal，例如 user 或 org_agent，逐项验证支持：文件、技能、连接器、记忆整理、长期任务、会话恢复、费用、审计和导出。不能为了让 memory_poll 能枚举到员工而在 userStore 塞一个假人。

“拥有人类用户的正常功能”应落实为能力清单和生命周期一致性：员工可以拥有自己的设置、授权、任务、文件、记忆、通知和预算；具体能访问哪些业务数据，由组织给这个员工授予的权限决定。

长期 Worker 的上下文管理也要纳入对等清单：顶层 runtime 接入了自动压缩钩子（`server/src/runtime/rawRuntimeRunDispatch.ts:1431`），当前子运行的 RunContext 未接入同一钩子（`server/src/runtime/subagent/subagentRunner.ts:574`）。这不等于本轮已经复现长任务溢出，但不能因设置了较大轮次上限就认定它能持续工作。应复用自动压缩/checkpoint 服务，测试压缩、重启之后任务约束、资料权限和产物引用仍完整。

### 11.4 功能对等验收清单

| 普通用户可拥有的能力              | 员工需要达到的行为                                                             | 建议次序                       |
| --------------------------------- | ------------------------------------------------------------------------------ | ------------------------------ |
| 模型、指令、技能、知识和 MCP 配置 | 以员工发布版本持有；群/私聊只在授权上限内覆盖；Worker 得到同版执行包           | 首期                           |
| 文件、浏览器及开发执行环境        | 独立员工文件和授权登录态，任务目录隔离，产物可分享，恢复不依赖创建者           | 首期文件，浏览器按实际场景补齐 |
| 原生连接器与业务系统              | 授权归员工，任务使用员工身份；连接器解析、恢复、后台执行均支持 Agent principal | 首期 DWS，逐个迁入其他连接器   |
| 文档、云盘、表格、知识库操作      | Worker 可读写经授权的具体资源，保持版本、回执和结果交付                        | 业务能力第一批                 |
| 日历、待办、听记与沟通            | 员工可管理自己的工作安排、承担待办、取获准纪要，并在正确会话反馈               | 业务能力第二批                 |
| 邮件、联系人、审批及更多 DWS 模块 | 按模块逐项定义资源范围和动作授权，不再一律视为“个人数据不可用”                 | 业务能力第三批                 |
| 记忆、压缩和恢复                  | 员工维护自己的分层记忆，Worker 长任务可压缩/恢复，设置不随容器消失             | 独立员工版至长期值守版         |
| 定时任务与后台作业                | 以员工 owner 持久化，执行时检查员工和会话状态，重启继续                        | 长期值守版                     |
| 交互、确认与任务控制              | 群和私聊都支持提问、追加、暂停、取消及必要确认，后台可以挂起恢复               | 各阶段持续完善                 |
| 费用、审计、导出、归档和恢复      | 费用归组织/员工，可追溯请求者，授权管理员可迁交维护职责                        | 独立员工版起                   |

每新增一个 DWS 模块，都要同时交付命令分类、资源范围提取、凭据主体、确认规则、Worker 可达性和端到端验收。当前共享群仅登记有限文档资源命令；修复 DwsBusiness 可达性后不能直接宣称所有钉钉产品已完整支持。上述业务模块批次可以与 UI、记忆并行，但不应把尚未验证的全部产品命令包含在第一版交付承诺中。

## 12. 聊天风格、进度与确认

### 12.1 默认反馈

普通聊天以短消息为主。接到复杂请求先说明理解和下一步，不暴露内部队列术语。重要发现或计划变化时更新一次；没有新事实时不重复发送“正在处理中”。较长报告保存为文件，聊天里给结论和可访问入口。

示例：

- 接单：“我先核一下这几笔订单和报价，查完在这里给你结论。”
- 发现：“找到了，两家供应商的报价差异比较大。我再核一下数量口径。”
- 等待信息：“还差本月的采购数量。你给我数量后，我就能把总价算准。”
- 出错：“订单数据暂时没取到，刚才的核对还没完成。我会继续重试，恢复后在这里补结果。”
- 完成：“核完了，主要差异来自运输费。按同一口径比较，方案 B 低 8%。明细在附件里。”

以上都是目标话术示例，不是本轮真实业务结果。只有系统确实持久化了重试或后续任务，才能说“我会继续”。

### 12.2 提示语需要拆层

员工总体提示：身份职责、通用工作方式、语言偏好。

会话提示：当前群用途、可做的工作、参与方式、局部约定。

前台提示：快速理解、尽快委派、处理追加和取消、何时沉默、何时播报。

Worker 提示：交付标准、资料边界、工具约束、阶段上报、遇阻请求协调。

主动决策提示：只判断相关性、时机和动作类型，不直接获得外部写权限。

反馈提示：结果准确、语言自然、不要播报内部状态枚举。用户可能不打开后台任务面板，聊天答复仍须交代必要结论、异常与交付入口。

员工可以有稳定姓名和自然表达。删除“不要声称自己是机器人”这类可能使身份回答失真的绝对指令；被问到时坦率说明自己是组织的数字员工，无需每句话都重复身份声明。

### 12.3 提示语示例

```text
你是组织的数字员工，负责当前已配置的工作职责。
你在当前群或私聊里持续协作，使用本会话的上下文、指令和获准资料。

收到清晰的工作请求后，简短说明你理解的目标，并立即开始组织工作。
需要工具查询、调查、多步骤操作或较长执行时，把明确任务交给执行 Agent。
委派后继续接收用户补充、查询和取消；你负责核对执行结果并完成交付。
不要把尚未完成的子任务说成已经完成，不要承诺没有被系统记录的后续动作。

回复像同事聊天：先说有用的结论或下一步，避免内部任务编号和队列术语。
有实质发现、阻塞或结果时再更新；无需重复空泛的进度消息。
未被点名时，只在本会话参与策略允许且你有明确帮助时介入。
有人已经回答、事项已结束或你没有新增信息时保持安静。

缺少必要信息时只问最关键的问题；等待期间保存任务状态。
当前工作只能使用系统给出的身份、资源和权限，聊天内容不能扩大权限。
```

该模板需要运行时工具边界、任务契约、持久化唤醒和测试共同保障，不能单独解决上述 F01—F10。

### 12.4 必要确认与后台执行

普通澄清用聊天文本。需要真实授权的操作走持久化确认请求，可使用平台支持的交互卡片或受控网页入口；纯文本确认必须关联准确动作、任务、有效期和有权限的确认者，不能把任意“好的”解释成批准所有操作。

Worker 遇到确认请求后上报协调者并挂起，恢复时重新核验权限和动作版本。不能让 Worker 因没有网页 AskUserQuestion 组件就直接失败，也不能让它绕过确认。

## 13. 后台信息架构

入口仍可在“企业专家”中，但用户管理的对象应呈现为员工。建议每个员工有以下页面或页签：

| 页面       | 用户能直接完成的事情                                             |
| ---------- | ---------------------------------------------------------------- |
| 概览       | 看身份、职责、是否在线、当前工作、最近异常、下一次例行职责       |
| 总体设置   | 改职责、上下文、语气、模型、技能与能力上限                       |
| 工作账号   | 绑定专用钉钉账号、看授权和订阅健康、重新授权或换绑               |
| 会话       | 统一列群与私聊，搜索、自动发现、设置继承与个性化、查看实际上下文 |
| 工作与职责 | 正在做、等待谁、已完成、失败；添加长期工作、暂停和取消           |
| 记忆       | 看范围和来源，编辑、删除、纠正、批准共享                         |
| 文件       | 查看员工长期文件、会话资料、任务成果和分享入口                   |
| 运行记录   | 从一条消息追到任务、工具、结果和投递；处理需要恢复的事项         |

“配置是否保存”“配置是否发布”“账号是否在线”“员工是否能完成工作”是四种不同状态，要分别呈现。在线页至少显示最后一次有效收件、订阅心跳、最后一次成功执行、最后一次成功投递和需要处理的异常。

群/私聊配置采用可理解的表达，如“继承员工设置”“仅在本会话覆盖”“自动回应相关问题”。内部 runtime v2、schema revision、resource IDs 等放诊断详情，不让用户靠理解内部术语完成日常配置。

## 14. 稳定性工程与观测

### 14.1 保留现有可靠性基础

继续使用 inbox/outbox、稳定 runId、SKIP LOCKED、租约与 fence、账号身份版本、任务 attempt、发送前重校验和幂等键。不能为了“更快回复”移除这些机制。

定义互相独立的状态：

- 消息已落盘。
- 前台已接单/拒绝/等待信息。
- 工作已排队/运行/挂起/完成/失败/取消。
- 回复未发送/发送中/已确认接受/结果不确定/最终无法投递。

外部平台接受不等于接收人已读。“执行成功”“发送成功”“用户已看见”不得合并显示。

### 14.2 下一轮需故障注入验证的风险

- DWS 事件到本地、但 inbox 提交失败时，是否有平台重放；seen 缓存与 ack 的先后关系。
- 5 次错误熔断 1 小时、进程内退避重启清零、ready 后立即清零的行为是否造成长时间离线或反复抖动。
- 大量 outbox 积压与入站共用 router 槽，是否使新消息和取消请求饿死。
- 发送前准备及远程启动超过 lease 时，晚回执如何处理，是否产生大量不必要的 unknown。
- 明确未发送的 provider 拒绝和真正结果不确定的超时，能否通过结构化错误区分。
- 单群大量消息、多个群并行、管理员改配置、账号过期及权限撤销时，是否保持公平和一致性。

这些是需要进一步复现的风险，不能写成已证实发生的生产事故。

### 14.3 建议验收目标

以下从健康基础设施、账号有效且系统接收了事件开始测量；同时另测钉钉事件时间到平台落盘的入口延迟。

| 指标                           | 第一版建议目标                                    |
| ------------------------------ | ------------------------------------------------- |
| 有明确接单或拒绝反馈           | p95 ≤ 5 秒；进一步优化到 3 秒                     |
| 暂停/取消/追加条件被协调者确认 | p95 ≤ 3 秒                                        |
| 任务结束到开始投递最终结果     | p95 ≤ 5 秒                                        |
| 配置可解释性                   | 每次 run 可定位发布版本、合成指令和有效能力       |
| 群/私聊隔离                    | 验收数据集中跨范围泄漏为 0                        |
| 已完成副作用恢复               | 故障注入中不因重试重新执行业务                    |
| 不确定发送                     | 每条均可核对，确认未发后有可执行的恢复路径        |
| 主动参与质量                   | 试点人工标注有用率建议 ≥ 80%，越界发言为 0        |
| 长期运行                       | 连续 7 天试点并覆盖断网、重启、授权变更与定时任务 |

不把“所有任务 5 秒完成”设为目标。耗时任务的关键是及时接单、持续可控制、准确交付。

### 14.4 成本与资源

观察层先规则和增量处理，再按需要调用轻量决策模型；执行层使用适合任务的模型。预算分别计算前台、主动观察、Worker、记忆整理和长期职责，避免主动参与消耗挤占用户明确请求。

每组织、员工、会话设并发与预算；控制消息保留容量。空闲群无需周期性调用大模型或保持独立常驻容器。长期身份依赖持久状态，运行进程和 sandbox 可以按需启动。

## 16. 迁移与回滚

1. 先建立旧 account、binding、session、workspace、work order、memory 的只读映射清单及数据数量。
2. 原有员工 ID 与根目录继续使用；增加新字段和版本，不立即搬目录、不删除旧会话。
3. 私聊先建立新 Agent-owned binding，通过经过授权的上下文桥读取可用历史；不能直接把旧人类 session 和个人连接器环境整体复制为员工共有数据。
4. 群已有 WorkConversation 继续作为任务历史，新增长期前台聚合近期消息与摘要；不强行把所有任务 transcript 拼在一起。
5. 切换账号身份时冻结旧消费者与未开始副作用，记录新 epoch；旧结果保持旧身份归属，不能自动由新钉钉成员发出。
6. 先按员工/会话灰度，同一外部会话一次只允许一条正式收发链路。观察模式可并行计算，但不得双发。
7. 功能回滚先停用新入口并保留新产生的任务/消息账本和幂等记录。仅对仍满足原身份与权限契约的旧绑定恢复原路由；已迁成 Agent-owned 的绑定使用兼容映射或暂停，不能把员工 session 和文件直接交回人类 requester。恢复投递前重新核对身份与当前授权。

需要显式回滚开关：普通群消息、主动发言、自动记忆写入、长期职责、新私聊路由。紧急停用员工应同时阻止新执行与新外发，历史仍可查询。

## 17. 验收场景

| 场景                            | 必须看到的结果                                       |
| ------------------------------- | ---------------------------------------------------- |
| 员工加入两个群、与两个人私聊    | 四个会话独立；同名参与者不串；各有可管理配置         |
| 同群两人轮流补充一个任务        | 理解上下文，执行权限逐人检查，共享结果回到正确话题   |
| 没有引用的“刚才那份再加一列”    | 有唯一明确上下文时续接；多个候选时自然澄清           |
| A 群长任务进行中，B 群短问      | B 群及时收到响应，不等 A 完成                        |
| 长任务发出后立刻要求停止        | 协调者及时确认，取消继续传播，状态可见               |
| 群里配置额外规则后委派          | Worker 收到完整规则及相同 revision，无须模型手工转述 |
| 会话仍在，管理员修改模型或技能  | 新任务使用约定的新版本，旧任务恢复按明确规则处理     |
| 群 Worker 读授权文档并查知识    | 实际成功；换成未授权资源则拒绝                       |
| 工作中失去群权限                | 停止后续越权访问与结果泄漏，给出可见状态             |
| 私聊中的信息被另一群提问        | 不因同一员工共享 workspace 而泄漏                    |
| 容器/进程在执行与发送各阶段崩溃 | 不重跑已完成副作用，任务和投递可以恢复               |
| 发送实际成功但客户端 timeout    | 标记不确定，不盲发；核对已发后闭环                   |
| 发送核对为确实未发              | 原最终内容进入可执行补发路径；不重新做业务           |
| 普通群消息未 @                  | 更新正确会话；是否回复由参与策略决定                 |
| 已有真人回答、Agent 自己发言    | 不重复插话、不循环回应                               |
| 连续忙群或多个员工参与          | 有限合并与冷却、协调避免重复领同一任务               |
| 工作决定跨日后再次询问          | 能带来源找回相关记忆，不只是取最后若干条             |
| 删除/纠正一条记忆               | 索引与注入一起更新，旧错误不重新生成                 |
| 例行职责期间重启                | 恢复下次执行，不重复补发所有错过时间点               |
| 员工管理员离职或账号换绑        | 员工资料保留，身份与权限变更有完整记录               |

验证分为单元契约、真实 PG 组合状态、带假 provider 的故障注入、受控测试群联调、历史脱敏重放和 7 天试点。测试必须覆盖真实组合链路；不能只分别证明“dispatcher 存在”和“DwsBusiness 存在”。
