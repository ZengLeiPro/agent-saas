## 一、总体判断

这个项目已经不是缺少基本工程保障的原型。它有跨工作区契约、相当规模的自动化测试、服务端权威授权、运行恢复与幂等机制、生产制品身份、迁移门禁、发布对账和移动端身份治理。基线提交的 Linux APP CI、ACS CI、测试环境部署、生产发布工作流都成功；本地各端类型检查、主要客户端测试、SDK 测试、构建也提供了实质性证据。

但“正常路径和现有测试通过”不等于跨进程、异常存储、身份切换、网络流和故障恢复边界全部成立。本次最值得优先处理的，是以下五组具体问题：

1. **身份与业务数据的持久化边界**：UserStore 可以在并发创建时产生重复用户名，也可以由旧实例快照覆盖新数据；部分读取失败被当作空库，后续写入会破坏原件；AuthEpoch 的全文件更新没有统一跨进程事务。这里应该先修数据完整性，而不是先拆大文件。
2. **客户端身份与本地文件边界**：正常 token 续期会误伤同身份的并发成功请求；移动端在途文件下载没有完整的身份隔离与退出清理；部分原生下载、本地锁能力探测和 Web 存储失败语义没有服从统一认证边界。
3. **完成、锁和恢复之间的交接**：Cron 锁连接丢失缺少本地失效管理，任务执行结束与通知交付没有 durable handoff；不同真实部署路径可能产生不同 Cron 锁名；启动清理不能把不完整扫描当成确定缺失。
4. **安全声明强于实际技术保证**：HTML 预览的隔离阻止了读取父页面身份，但不能按当前策略保证禁止所有联网；回环内部路由与反向代理组合后不能代表原始请求来源；出站请求的超时和字节预算没有完整覆盖响应体。
5. **发布与验证闭环存在具体空隙**：Evidence Writer 的不可变文件发布、失败重试与恢复分支还有风险；CI 有覆盖率完整性和检查范围缺口；依赖扫描有实际业务可达的受影响解析库，不能仅按工具严重度排序，也不能忽略。

报告登记 **46 个独立 review 项**：安全 5、运行时与数据 12、Web/Shared/Mobile 16、发布运维 7、依赖治理 3、工程质量 3。这不是“46 个已经发生的线上 bug”：其中包含隔离复现的缺陷、源码确认的条件风险、容量/维护性问题，以及明确尚未完成的发布验收。每项的适用条件、证据层级和关闭标准都在专项章节内。

本次没有取得足够证据认定正在发生的生产 P0 事故，也没有取得足够证据给整个线上系统出具“安全无问题”证明。最合理的处理方式是按下文分批解决确定性问题，再用只读环境取证决定条件风险的实际优先级；不需要根据这份报告直接停服、清库、重发全部任务或进行大规模重写。

## 五、应当保留的既有设计

修复这些问题时，最容易出现的第二次事故，是为了局部通过而撤掉原本正确的保护。下面这些不是待重写清单：

- **Canonical 授权**：HTTP 会读取治理身份，密码重置已采用 canonical Membership。不要重新相信 JWT 旧 role，或用前端入口隐藏替代后端授权。
- **身份代际**：请求/WS fence、认证 journal、标签页权威存储、原生可信 origin 已存在。UX-02 要区分同身份续期与真实身份变化，不是取消旧身份响应拒绝。
- **持久执行恢复**：RunStore CAS、稳定幂等键、session 租约、终态 outbox、取消投递与 NOTIFY 补扫已有实现。REL-05 是 Cron 外层交付缺口，不需要重做整套 Runtime。
- **PG 提交顺序设计**：全局 writer 锁和全局读取屏障有正确性目的。性能优化不能直接删锁，也不能把 sequence 当天然提交顺序。
- **ACS 资源身份**：UID/resourceVersion fence、finalizer、lease、容量 reservation、后台 Shell 保护与 drain 有实际代码。不要按资源名字清理同名新实例。
- **Worker 准入**：readiness 不只是进程存活，还绑定 ConfigIdentity、私有快照及 retention 等条件。不能为了让 503 消失而伪造 readyfile 或跳过身份核验。
- **发布身份和门禁**：APP CI 数字 workflow identity、不可变制品、迁移后置条件、Staging 最终状态、生产互斥和公网 JS/CSS 字节读回应继续保留。
- **客户端已修行为**：前台恢复合并、Web 网络三态、业务步骤结束态和最终答案独立完整的指令已存在；不把历史问题重复列为未修复。
- **供应链基础约束**：冻结锁文件、精确工具版本、pnpm 校验、最小发布年龄和有限安装脚本白名单有价值。升级依赖不是解除这些约束的理由。

## 八、长期维护建议

### 让“权威”在接口中可见

本次问题反复出现的根因，是局部 API 返回值隐藏了关键事实：空数组可能是读取失败；成功可能只是 mirror 写成功；terminal 可能只是业务结束但通知未交付；一个 URL 校验通过不代表实际连接到同一地址；一份 coverage JSON 不代表所有分片都在。建议把这些隐含状态显式化，例如 `complete/errors`、`committed revision`、`identity generation`、`lock lost`、`delivery pending`、`evidence incomplete`。不要求所有接口改成同一套复杂框架，但要求危险动作在使用事实前验证事实的完整性。

### 先定义生命周期，再决定存储或组件拆分

需要清楚画出的生命周期包括：身份建立→凭据续期→身份切换→旧响应失效；下载启动→锁定/退出→迟到完成→缓存/分享释放；锁获取→租期/连接失效→停止执行→恢复；业务完成→持久交付→外部结果未知→幂等重试。很多问题不是再加一个 catch 就能解决，catch 若把未知变成功，反而会扩大风险。

### 度量关键边界，而不是追求漂亮总分

不建议给这个仓库一个“健康度 85 分”作为结论。没有真实负载、事故率、备份恢复和产品目标就没有可信评分模型。更有用的固定指标是：身份漂移拒绝按原因分类、迟到下载丢弃、文件完整性失败、锁丢失与重复 claim、通知 backlog/dead letter、事件投影 lag、PG pool wait、scheduler 最近进展、证据 incomplete、真实设备回归通过率。

同样，不建议一次性追求零 lint warning、100% coverage 或所有文件少于某个行数。先对新增风险设门槛，给历史例外负责人和到期条件，再逐步压缩。生成文件与手写权威逻辑应分开，测试 helper 的 any 与真实外部输入边界也应分开。
