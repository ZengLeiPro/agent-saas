## 审查结论与证据口径

现有身份治理已有相当多正确的防护：HTTP 请求会重新读取治理身份，不直接相信 JWT 中的旧角色；密码重置已应用 canonical Membership；会话撤销有持久化 epoch/generation；文件操作使用 Linux 文件描述符约束；生产 nginx 日志避开 query token。这些都应保留。

本次主要风险在于**进程、反向代理和网络流的边界组合**。单个函数局部看似正确，组合部署后不一定仍满足原先的安全承诺。下列五项均有当前源码依据，但没有把“源码存在风险路径”写成“生产已被利用”。

## SEC-01：内部浏览器 API 的来源判断与反向代理冲突

### 证据与调用关系

- `server/src/index.ts:237` 将 `/internal/browser` 注册在普通应用监听器上，只检查 `req.socket.remoteAddress` 是否是回环地址。
- `server/src/index.ts:250` 的认证中间件仅挂载到 `/api`，不覆盖这个内部路由。
- `server/src/routes/browser.ts:89` 建立浏览器路由；它的实例启动、停止操作通过请求中的 username 选择浏览器，没有另外绑定已认证调用者。
- `daemon-packaging/nginx/agent-api-kaiyan.conf.example:95` 的 HTTPS `location /` 转发到应用 upstream，未排除 `/internal/`。
- `daemon-packaging/nginx/agent-saas-staging.conf.template:25` 同样转发全部剩余路径到回环 API upstream。
- `docs/ecs-direct-deployment.md:28` 描述的实际部署拓扑也是公网 nginx → `127.0.0.1:3200/3201`。

反向代理连接后端时，后端 socket 的对端是本机 nginx。这一事实不能证明最初发起请求的是本机 Agent。`trust proxy` 的配置也不会改变 socket 对端地址；把这个检查简单替换为一个未经可信链约束的请求头，同样不能建立服务身份。

### 触发前提与影响

需要同时满足：实际代理保留随仓的全路径转发，代理以回环地址连接应用，应用运行 HTTP/API 入口，内部路由未另被外部 ACL 阻断。`server/src/index.ts:187` 的 scheduler-only/runtime-worker 分支会在创建 HTTP app 前返回，因此该项不是 Worker 专用监听器的缺陷；`all`/`ws-only` 的普通 HTTP 入口才是这里的范围。浏览器控制动作还依赖 browser-ports 配置、对应用户映射和本机浏览器运行条件。该路由硬编码 macOS Chrome 路径，因此不能据此直接推断 Linux 生产机存在可工作的浏览器实例，也不能把它夸大为已经证明的任意代码执行。

确认的问题是：被称为 localhost-only 的管理能力，缺少端到端的来源身份保证。在实际可用环境中，可能影响其他用户的浏览器生命周期和其正在执行的任务。即使当前生产没有浏览器映射，也不宜继续把一个历史内部接口无条件挂在公共监听器上。

### 修复设计

1. 明确此功能的支持范围；若仅服务本地开发/旧本机模式，通过显式能力配置注册，并让生产默认不注册。
2. 将内部控制面放到单独 Unix socket 或专用监听器。公共 HTTP 监听器只注册对外协议；必要时保留明确的内部客户端认证和最小权限。
3. 公网及测试环境 nginx 增加内部前缀拒绝规则，作为纵深防护。不要只修一份 example：同时检查安装脚本、template、recovery 入口和相关配置测试。
4. 对浏览器操作绑定调用者、tenant/user 和允许的实例。管理员代操作必须是独立、可审计的能力。
5. 对子进程添加启动失败处理，明确不支持的平台返回结构化不可用，不让异步子进程错误破坏 API 服务。

### 验收与实施成本

用隔离 HTTP/代理 fixture 验证：经过本机代理的外部请求不能访问内部管理动作；授权内部客户端可正常工作；普通 API、WS、上传不受影响；Linux 未启用此能力时明确不可用。最后由运维只读核对已安装 nginx 的有效配置，而不只检查仓库示例。

估计 1～2 人日，另需一次部署配置核验。优先于对内部浏览器功能的扩展。

## SEC-02：会话撤销权威在多进程下缺少原子更新

### 证据与根因

- `server/src/auth/authEpochAuthority.ts:78` 的 `fence()` 先 `load()`，修改单个用户记录，再提交整个 users 映射。
- `server/src/auth/authEpochAuthority.ts:94` 的 `revokeGeneration()` 和 `:132` 的 `issue()` 采用同一模式。
- `server/src/auth/authEpochAuthority.ts:171` 读取完整 JSON；`:189` 以带 PID 的临时文件写出，然后 rename 到权威路径。
- `server/src/app/runtimeAuthInitialization.ts:26` 在每个运行进程构造指向 users 文件旁 `auth-epochs.json` 的 authority。

rename 保证读者不会看到一半新文件，但不保证两个进程的“读取旧值—计算新值—发布”作为一个整体串行执行。同一进程同步调用的顺序性，不能替代蓝绿 API、多实例或其他进程之间的互斥。不同用户的修改也可能相互覆盖，因为写出的是整个映射。

复核了上层调用：`server/src/routes/authResponse.ts:29` 直接签发 binding；`server/src/auth/middleware.ts:78` 直接执行旧 token 升级。`runtimeAuthInitialization.ts:35` 附近确实存在 PG advisory lock，但它传给的是 TenantStore，并不包围 AuthEpochAuthority 的读改写。因此不能用相邻的租户存储锁解释为此权威已有跨进程保护。

### 影响与适用边界

在两个可写实例共享同一权威文件时，某次登录可能丢失，用户表现为刚登录又失效；更重要的是，另一个进程从旧快照发布后，已持久化的撤销结果可能被覆盖，违反 epoch 只前进的承诺。该项是跨进程时序风险，并不是“每次退出都会失败”，本次没有完成跨进程安全复现，也未读取线上实例/数据状态来判定发生频率。

现有文件读取、JSON 解析或旧记录转换抛错时，会产生 `AUTH_EPOCH_STATE_CORRUPT`，HTTP 认证链会转换为身份服务不可用，这个拒绝继续授权的行为应保留。需要准确限定：`:175` 只在 version/users 的浅层条件满足时接纳新状态，其他合法 JSON 形状可能被忽略并保留内存状态，不能描述为已经具备完整 schema 的 fail-closed 校验。修复时应补齐版本、结构及字段不变量校验，但不要为提高可用性把损坏权威自动重置为空。

### 修复设计

推荐将 authority 变为数据库中的用户级记录，在事务内执行单调递增和 generation 集合变更，使用行锁或 CAS。更新应返回已提交的 binding，成功响应和撤销通知均以提交结果为准。进程内缓存必须有失效语义；需要立即撤销的路径不能只靠长 TTL。

若短期仍采用文件存储，必须对**整个读取、校验、计算、写临时文件、提交**加跨进程锁，并核实共享文件系统的锁语义。只在 rename 周围加锁没有用；只给每个 UserStore 实例加 Promise queue 也没有用。

迁移需要版本化：先建立新权威及回填校验，在所有写入者都能识别新权威后再切换，处理 N/N+1 并存阶段；不能直接初始化 epoch=1 或把旧权威覆盖掉。对账至少包括当前 epoch、最后 generation、active generations 和撤销原因。出现不一致时以不降低已确认撤销状态为约束，不能默认挑“最后修改时间最大”的整个文件。

### 验收与成本

需要两个独立进程的测试，覆盖同用户并发登录、退出与登录交错、管理员撤销与其他用户登录交错、提交后进程退出、磁盘/数据库不可用。断言 epoch 永不回退、同一 generation 不重复签发、撤销不会被恢复、失败不会返回成功。单进程 Promise.all 测试不能替代这一组。

估计短期防护 1～2 人日，数据库化及兼容迁移 3～5 人日。与 REL-01/REL-02 同属持久化治理，但这是认证权威，宜单独评审。

## SEC-03：Hand URL 解码异常缺少请求级边界

### 证据

`hand-server/src/index.ts:100` 使用原生 `createServer` 回调路由请求。`:129` 匹配 invocation 路径，`:131` 在进入处理器之前调用 `decodeURIComponent`；workspace 生命周期路径 `:141` 至 `:148` 也直接解码。回调外没有捕获解码异常的边界。

`decodeURIComponent` 对非法编码可以同步抛出 URIError。原生 HTTP RequestListener 不会像某些 Web 框架那样自动将这里的同步异常变成 400。处理器内的认证或 try/catch 已经来不及处理路由解析阶段的错误。

### 影响与限定

默认 Hand 只监听回环地址（`hand-server/src/config.ts:139`），风险首先属于可达该监听器的本机调用方；若按配置开放容器网络或组织 ECS 内网，则可达范围扩大。不能把它直接称为公网未认证漏洞。主要后果是未捕获异常导致进程退出、在途 invocation 中断，以及重启后的不确定结果对账；即使 supervisor 自动重启，也不能恢复该请求边界或消除在途任务影响。

### 修复与验收

增加统一请求入口：安全解析路径，限制标识长度和字符集，将解码失败稳定返回 400；每个异步路由都有统一拒绝处理，响应是否已发送需要被考虑。捕获单个请求错误不等于吞掉不可恢复的进程错误，二者应有不同日志和退出策略。

回归覆盖非法编码、合法中文/Unicode ID、保留分隔符、GET/取消/归档方法边界和未知路径；请求失败后同一进程的健康检查和合法调用仍成功。默认回环监听和对外部署的来源 ACL 都应保留。与 OPS 中的 Hand 自有测试未进入 CI 一并修复。

估计 0.5～1 人日。本专题没有提供攻击载荷，也没有连接实际 Hand 服务。

## SEC-04：KY App 出站的超时、大小和取消仅部分生效

### 证据与实际行为

`server/src/kyapp/outbound.ts:159` 先等待包括 DNS 校验在内的目标解析；`:167` 至 `:171` 随后才建立 AbortController/计时器；`:179` 等待 fetch；`:194` 的 finally 在 fetch 返回响应头后就清理计时器，并移除外部 signal 的监听；`:206` 随后执行 `response.text()`，读完所有内容后才 `.slice(0, maxBytes)`。`:200` 的拒绝重定向分支直接抛错，没有消费或取消响应体。

因此以下细节与上层承诺不符：

1. fetch 完成响应头不代表响应体结束，“15 秒硬超时”不覆盖后续 body 读取。
2. 外部取消在这时已解绑，run 取消未必能结束正在读取的响应体。
3. `.text()` 会先完整缓冲，不是 256 KB 内存上限。
4. `.slice()` 按 UTF-16 字符单元截断，不等于协议定义的字节上限；读取错误被转换为空字符串也会抹去失败语义。
5. 目标 DNS 校验也在计时器启动之前，不属于目前这份硬超时；提前拒绝重定向时，应用层没有确定地释放该响应流。

上层并非没有保护：`server/src/kyapp/gateway/lcid.ts:185` 设置逻辑调用总截止，`:334` 将剩余时间下传为单次预算；`:388` 在结果返回后执行输出字节预算（默认 6,000 字节），`:395` 附近还检查 HTTP 200 的业务 JSON 形状。但是总截止是在循环边界检查，`:216` 仍直接 await outbound，不能中止已卡在其内部的 body 读取；输出预算同样发生在完整缓冲之后，不能替代传输内存上限。Staging 的 `server/src/runtime/egressDispatcher.ts:263` 代理 fetch 返回 Response，也没有补上 body 消费的生命周期预算。

### 触发条件与影响

只需一个已登记的定制应用返回慢响应体、异常大响应或中途断流，不依赖它突破 host 白名单。可能导致能力调用迟迟不结束、内存放大、取消失效，或把 body 读取异常压成仍携带 HTTP 200 的空 transport 结果。这里不能说所有上层都会误报业务成功：LCID 的 JSON 形状检查会将空结果判为 `internal`，health prober 也会判为失败；问题是原始断流/超时类别被丢失，降低排障及重试判定的准确性。这是对合法上游故障也适用的可靠性问题。

健康探测同样复用此组件：`server/src/kyapp/health/prober.ts:100` 串行遍历 installation，`:137` 直接等待 outbound，没有额外 body 截止。某个实例卡住响应体时，同一轮后续实例的探测也可能被延迟；不等同于已经确认整个服务必然耗尽内存。

### 修复设计

- 在统一 try/finally 中完成目标解析、连接、响应体消费、解析/返回和清理，让 deadline 覆盖整个操作；若 DNS 单独有预算，明确计入总预算。
- 通过 reader 增量读取并统计字节；达到上限立即 cancel/abort，返回明确的 `response_too_large` 或约定错误。Content-Length 只能辅助，不能代替流式计数。
- 保留外部 signal 监听直到 body 处理完全结束；区分超时、上游错误、调用者取消，避免取消被重试。
- 拒绝重定向等分支也释放响应体；不要吞掉 body 读取失败后继续按 HTTP 200 返回。
- 如果复用通用 WebFetch 的流式限长实现，应保留其已有 reader 字节计数和超限 cancel（`server/src/agent/web/ssrf.ts:196`），同时补齐重定向和仅凭 Content-Length 提前拒绝分支的 body cleanup（`:117`、`:184`）；不要把现有 WebFetch 的流式读取错误描述成与 KY App 一样完全无限缓冲。
- 在能力层记录受控指标：耗时、读取字节、取消原因和 installation/request ID，日志不包含 SAT 或完整业务正文。

### 验收与成本

本地可控 HTTP/流 fixture 覆盖正常小 JSON、响应头快速但 body 延迟、无 Content-Length、分块越限、多字节文本、中途断流、响应头之后取消。断言截止时间内完成、网络流已关闭、超限不会完整缓冲、错误不会变成空成功。无需构造大规模资源耗尽测试。

估计 1～2 人日。修复应应用于真实出站组件，不能只在调用方再套一个不取消底层 I/O 的 Promise.race。

## SEC-05：DNS 校验与实际连接地址没有绑定

### 证据与适用范围

`server/src/agent/web/ssrf.ts:63` 解析 hostname 并验证所有返回地址；该方法最终只返回 URL。`:84` 至 `:88` 使用 hostname 调用默认或注入的 fetch，未把已验证的地址或对应 dispatcher 传给连接层。KY App 出站 `server/src/kyapp/outbound.ts:144` 也调用此校验后再使用 fetch。

已有防护是正确的：只接受 HTTP(S)、拒 userinfo；调用者配置 allowedHosts 时执行精确 hostname 白名单；默认拒绝私网/回环/保留地址（调用方显式允许私网时另论）；WebFetch 重定向逐跳校验，KY App 更直接拒绝重定向，并使用登记 baseUrl 的精确 host 约束。通用 WebFetch 不是默认只有一个允许域名。这里的问题在于检查时与连接时的解析不是同一份已验证结果，不应被概括为所有 URL 防护均无效。

如果实际连接使用的 DNS 结果改变，或代理的解析视角与应用检查不同，连接的地址可能不满足刚才的检查。是否能访问不应访问的网络，还取决于当前 egress 代理、网络 ACL、元数据保护等。`server/src/app/runtimeStagingEgressBootstrap.ts:49` 要求 Staging full-proxy/fail-closed 并安装受控 global fetch；这保证出站路径受控，但此处代理调用没有携带刚才校验的 IP，最终目的地址策略仍需由代理和网络提供。不能仅凭默认 fetch 的实现断言所有环境均可越过网络边界。

### 修复设计与验收

将“解析—验证—连接”放在同一受控传输实现中：对已验证地址建立连接，保留原始 HTTPS hostname/SNI 和证书验证；重定向和重试重新执行同一规则。若由出站代理承接此责任，明确责任边界、禁止旁路，并验证代理本身的 DNS/目的地址策略。不要通过改写 URL 为 IP 后关闭 TLS 验证来解决。

回归使用注入式 DNS/连接适配器，验证第二次解析变化不会使连接跑到未验证地址；覆盖多 A/AAAA、IPv4-mapped IPv6、重试、代理和重定向。验收以实际连接目的地址为准，不只断言校验函数调用过。

估计 2～3 人日，优先与所有出站调用的统一治理一起做。没有在真实网络实施 DNS 行为探测。
