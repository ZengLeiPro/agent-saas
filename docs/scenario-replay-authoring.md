# 场景回放写作规范

> 2026-08-09 修订。目标读者：为能力中心编写销售演示剧本的人。
> 当前产品定位：所有手写场景均为**业务回放**，目标是讲清真正的业务价值与 AI 同事如何工作，不要求当前连接器或 Runtime 逐项兑现剧本动作。

## 0. 一句话

**回放是业务样片，不是连接器验收；说服力来自场景判断，不来自组件露出数量。**

`presentationToReplayScript` 只负责保底投影。销售要讲的重点场景应手写 `ReplayScript`，但不要再照 `complianceGateScript` 复制同一套七步骨架。

## 1. 先选场景价值，再选 UI 组件

每个剧本先回答五个问题：

1. 谁在什么时点会发起或被业务事件触发；
2. 不处理会损失什么；
3. Agent 读了哪些分散事实后，得出了人原本看不到的新判断；
4. 哪个动作真正改变业务结果；
5. 什么状态能让观众一眼看懂“这件事办完了”。

以下是可选的演示要素，不再要求每个剧本全部出现：

| 要素 | 适合什么场景 | 不适合时不要硬塞 |
|---|---|---|
| 主动拒绝 / 权限拦截 | 涉及隐私、越权写入、外部承诺 | 普通分析、会议追办不必先诱导一次违规 |
| 人工审批 | 花钱、对外发送、跨部门取舍、不可逆动作 | 纯只读分析或低风险草稿 |
| 对方视角 / 可下载产物 | 客户、供应商或管理者确实需要带走结果 | 每个 quick 都生成一页 HTML 会显得模板化 |
| 跨系统终态核对 | 多系统动作必须彼此一致 | 单一判断、单一输出场景 |
| 持续等待与升级 | 催办、交付、应收、客诉等长链路 | 一次性准备或分析 |

一个改变判断的事实，比“拒绝 + HTML + 审批 + ReadBack”四件套更有价值。

## 2. quick 与 hero

### quick

- 3～6 步；
- 只讲一个岗位问题和一个核心判断；
- 审批、产物、拒绝、跨系统表均按需；
- 适合销售快速点开，或空会话推荐入口。

示例节奏：

> 触发 → 找到关键信息 → 给判断与下一步 → 人确认（可选）→ 结果

### hero

- 5～10 步；
- 展示完整业务闭环；
- 至少有一个真正有业务意义的人工门禁；
- 有可带走产物、退回后的下文和终态核对；
- 适合重点行业或主打能力演示。

不要因为 hook 数量多，就把所有 hook 都按 hero 质量条款强制成同一种结构。

## 3. 共享演示世界

跨场景重复出现的客户、订单、采购单、物料、应收、客诉、人员和日期统一维护在：

```text
web/src/components/scenarios/replay/demoWorldFixture.ts
```

规则：

- 同一业务对象只定义一次；
- HTML、panel、Markdown 和正文从 fixture 派生；
- 同一事件可以从销售、采购、交付、老板等不同岗位观察，但事实不能变；
- 岗位视角必须回答不同问题，不能只是换标题。

例如：

- 交付风险回答“哪张订单会晚、为什么”；
- 物料短缺回答“缺口是否真实、该催谁、批准哪条采购动作”；
- 老板风险回答“相较昨天什么新增/恶化、为什么要升级给老板”。

## 4. 回放契约

### 一步 = 一次推进

```ts
{
  caption: "回放条显示的动作",
  blocks: [...],
  approval?: {...},
}
```

`blocks` 使用真实 `ApiTranscriptBlock`，继续走：

```text
mapSessionDetailToMessages → MessageList → MessageItem → ToolBlock
```

演示和真实会话共享渲染管线，但**不共享事实来源**。演示事实来自共享 fixture。

### 工具摘要

```ts
{
  title: "业务语言的一句话",
  detail: [...],
  status: "ok" | "warn" | "blocked" | "waiting",
  receipt: { id, system, readBack },
  panelBase: {...},
  panel: [...],
}
```

- 第一条工具块应提供 `panelBase`，避免首屏右侧空白；
- 每一步 `focus` 到本步真正变化的系统；
- 面板视图不超过 6 个；
- `detail` 写业务事实，不塞原始 JSON；
- 回放可以使用 `completed/readBack/live` 表达演示世界终态。

### 审批门禁

审批必须承载真实取舍，例如预算、对外口径、负责人、期限或跨部门授权。不要让人只改一句无关紧要的话来证明页面有审批组件。

审批场景必须提供 `rejectedBlocks`，退回后说明：

- 什么没有执行；
- 流程停在哪里；
- 如何修改并重新提交。

## 5. 回放标识

能力中心专区和回放头部统一显示：

> 演示数据 · 模拟完整工作过程 · 不会修改真实系统

不必在每个工具块重复解释，也不向客户逐项展示内部 `sources` 缺口。

精选演示卡与空会话推荐卡只提供“看回放”。真实试用、连接器接入和落地诊断放在完整目录或详情中，避免把演示入口与真实执行入口混为一谈。

## 6. `sources` 的内部用途

每个 `tool_use` 继续登记 `sources`：

```ts
{
  blockRef: "step3.tool.FinanceQuery",
  producer: "独立范围门禁",
  state: "needs-change",
  gap: "仍缺什么",
}
```

它用于内部制作评估、产品规划与项目报价，不是回放的发布门槛，也不在观众侧渲染。

- `exists`：当前已有同类产出方；
- `needs-change`：已有产出方，但展示结构仍需改造；
- `missing`：当前没有产出方。

不要为了让回放“看起来真实”篡改 `sources`；也不要因为 `missing` 就削弱演示故事中的完整闭环。

## 7. 文案红线

1. 第一问必须像岗位人员会说的话；
2. 订单额、暴露额、预计损失、ROI 和因果关系必须分清；
3. 观察不能直接写成因果，预测必须写前提与置信度；
4. 同一句话不要在工具摘要和正文重复；
5. 不出现真实客户名；演示数据必须具体且内部一致；
6. 不批量使用“一口气、一次改干净、全都、绝不遗漏”等同一修辞；
7. 人审写具体岗位和具体取舍，不写泛化“有权人确认”；
8. `**加粗**` 后不要紧跟会破坏 CommonMark 定界的中文全角标点。

## 8. 发布前自检

- [ ] `scenarioId` 与 catalog id 精确一致；
- [ ] 回放头部明确标识演示；
- [ ] 第一屏有 `panelBase`；
- [ ] quick 只讲一个核心判断，hero 才承担完整闭环；
- [ ] 场景步骤不是为了凑拒绝、审批、HTML、ReadBack；
- [ ] 跨场景事实来自 `demoWorldFixture`，没有金额、日期、库存、人数矛盾；
- [ ] 人审有真实业务取舍，退回不是死按钮；
- [ ] 有产物时正文用 `[FILE]` 引出；
- [ ] 每个工具块都有内部 `sources` 登记；
- [ ] `pnpm -F web typecheck` 通过；
- [ ] `registry.contract.test.ts` 与场景定向测试通过；
- [ ] `scenarios:lint`、`scenarios:sanitize-check`、`git diff --check` 通过。

## 9. 推荐制作顺序

1. 先选销售最值得讲的 3～5 个场景；
2. 建共享演示 fixture；
3. 先写场景的“新判断”和终态，再决定需要哪些步骤；
4. quick 与 hero 混排，不追求统一步数；
5. 写完一个就注册并跑测试，不攒一批后再统一修矛盾。
