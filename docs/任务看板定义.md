# 任务看板定义

## 1. 产品定位

任务看板是个人 Agent 工作事项的人工管理界面，位于「定时任务」下，与任务调度并列。

首期目标是把看板本身定义并落地，不实现自动认领、Cron dispatcher、并行派发、异常恢复等自动化 loop。

- 任务调度回答：什么时候启动什么任务。
- 任务看板回答：有哪些工作事项、当前处于什么阶段、补充了什么上下文、是否已人工确认完成。
- 两者首期互不驱动，不把看板状态写入 CronJob，也不把 Cron 配置复制进看板任务。

## 2. 首期范围

### 包含

- 个人多看板。
- 看板新增、重命名、编辑说明、归档与恢复。
- 任务新增、编辑、拖拽排序、跨列移动、归档与恢复。
- 任务详情、评论、关键词搜索、状态/优先级筛选。
- 乐观更新与 CAS 版本冲突处理。
- 桌面端与移动端可用。

### 不包含

- 自动认领、自动执行、Cron dispatcher。
- 子 Agent 并行派发、claim lease、异常恢复。
- 任务父子、阻塞、关联关系。
- 附件。
- 组织共享看板与成员权限。
- Workflow 画布。

## 3. 归属与权限

- 每个看板只归属一个用户。
- 用户可创建多个看板。
- 所有服务端读写同时校验 `tenantId + ownerUserId`。
- 组织管理员和平台管理员默认也不能读取或修改其他用户的个人看板。
- 看板归档后只读；恢复后重新允许写入。
- 任务归档后不出现在默认看板列，可在归档列表恢复。

## 4. 状态机

| 状态值 | 中文 | 定义 |
|---|---|---|
| `backlog` | 需求池 | 已记录，但尚未承诺进入近期处理 |
| `todo` | 待处理 | 已明确需要处理，等待开始 |
| `in_progress` | 进行中 | 已经开始处理 |
| `in_review` | 待复核 | 已提交结果，等待人工确认 |
| `blocked` | 已阻塞 | 因依赖、信息或条件不足无法继续 |
| `done` | 已完成 | 已经人工确认完成 |
| `canceled` | 已取消 | 明确不再继续处理 |

推荐主路径：

```text
需求池 → 待处理 → 进行中 → 待复核 → 已完成
                     └────→ 已阻塞
任意未完成状态 ───────────→ 已取消
```

首期全部操作都由看板所有者发起，因此允许人工跨状态纠正和重新打开；服务端记录新状态、Actor、时间与版本，不额外限制跳转路径。后续接入 Agent 工具时，再为 Agent Actor 增加严格转换约束。

## 5. 优先级

| 优先级值 | 中文 |
|---|---|
| `urgent` | 紧急 |
| `high` | 高 |
| `medium` | 中 |
| `low` | 低 |
| `none` | 无 |

默认 `none`。优先级不自动改变排序，用户拖拽顺序是列内展示真相。

## 6. 数据对象

### 6.1 Board

公开 API DTO（与共享类型 `TaskBoard` 一致）：

- `id`
- `name`
- `description?`
- `version`
- `archivedAt?`
- `createdAt`
- `updatedAt`

仅持久化层内部使用、不返回前端：

- `tenantId`
- `ownerUserId`
- `nextTaskNumber`

规则：

- `tenantId + ownerUserId` 是服务端所有查询的权限边界，不作为客户端可依赖的数据字段。
- 同一用户的活跃看板名称不可重复。
- 新建看板默认名称由用户输入，不自动生成隐式默认看板。
- `nextTaskNumber` 只增不减，用于生成看板内稳定任务编号；它是编号分配器状态，不属于公开 API。

### 6.2 Task

- `id`
- `boardId`
- `identifier`，格式为 `TASK-{number}`，在看板内唯一
- `title`
- `description`
- `status`
- `priority`
- `labels[]`
- `sortOrder`
- `dueAt?`
- `commentCount`，只读聚合字段
- `version`
- `archivedAt?`
- `createdAt`
- `updatedAt`

首期不放入 `cronJobId / runId / sessionId / claim*`。这些字段只有在自动化 loop 的执行协议确定后才增加，避免现在用假设污染模型。

### 6.3 Comment

- `id`
- `taskId`
- `body`
- `authorType`：`user | agent | system`
- `authorId`
- `authorName`
- `version`
- `createdAt`
- `updatedAt`

公开评论接口只允许用户新增 `user` 评论；`agent` 与 `system` 仅由服务端执行闭环写入。评论编辑和删除后置，避免修改历史上下文。

### 6.4 Execution

- `id`
- `taskId`
- `runId`
- `sessionId`
- `status`
- `requestedBy`
- `error?`
- `startedAt?`
- `finishedAt?`
- `createdAt`
- `updatedAt`

Execution 是任务与 Runtime Run/Session 的独立关联记录。Task 只表达业务状态，Execution 只表达某次 Agent 尝试；一个任务可随人工返工产生多次历史 Execution，但同一时刻只能有一条活跃记录。

## 7. 并发与排序

- Board、Task、Comment 都带从 `1` 开始的 `version`。
- 更新必须提交 `expectedVersion`。
- 版本不一致返回 HTTP 409，响应带当前对象，前端提示后重拉。
- 冲突后前端仅保留用户实际修改的 dirty 字段，其他字段采用服务端 `current`；重试只提交 dirty 字段，不能用旧整表单覆盖并发修改。
- 新任务默认追加到目标列末尾。
- 拖拽排序采用相邻 `sortOrder` 中点；必要时服务端对单列重新编号。
- 前端先乐观移动，失败后恢复旧快照并刷新当前看板。

## 8. 页面结构

### 8.1 入口

「定时任务」页面内增加二级菜单：

- `任务调度`：现有页面，URL `/cron`
- `任务看板`：新增页面，URL `/cron?view=board`

不新增一级 `AppTab`，不改造全局侧栏层级。

### 8.2 桌面端

- 顶部：二级菜单、当前看板选择、搜索与筛选。
- 主区：七列横向滚动看板。
- 卡片：编号、标题、优先级、标签、截止时间、评论数。
- 点击卡片：右侧详情面板。
- Header 操作：刷新、新建任务；看板管理放在当前看板菜单。

### 8.3 移动端

- 二级菜单与看板选择保留。
- 状态列改为单列状态切换，不强制横向展示七列。
- 任务详情使用 Dialog/Sheet。
- 不依赖 hover 才能出现关键操作。

## 9. REST 边界

基础路径：`/api/taskboard`

### Board

- `GET /boards?includeArchived=false`
- `POST /boards`
- `PATCH /boards/:id`
- `POST /boards/:id/archive`
- `POST /boards/:id/restore`

### Task

- `GET /boards/:boardId/tasks?includeArchived=false`
- `POST /boards/:boardId/tasks`
- `GET /tasks/:id`
- `PATCH /tasks/:id`
- `POST /tasks/:id/move`
- `POST /tasks/:id/archive`
- `POST /tasks/:id/restore`

### Comment

- `GET /tasks/:id/comments`
- `POST /tasks/:id/comments`

### Agent Execution

- `GET /tasks/:id/executions`
- `POST /tasks/:id/execute`，请求体只接受 `expectedVersion`

所有写接口使用 Zod 严格校验；PATCH 不接受所有权、版本、创建时间等服务端字段。

## 10. 第二阶段：单任务 Agent 执行闭环

第二阶段只增加由用户明确触发的单任务闭环，不自动扫描任务列：

1. 仅 `todo` 任务可点击「交给 Agent」。
2. 服务端在同一事务内新增 Execution 并把任务移入 `in_progress`；同一任务同时只允许一条活跃 Execution。
3. Execution 独立保存 `runId / sessionId / status`，不把运行字段塞回 Task。
4. Runtime Worker 真正 wake 前重新读取任务和最新评论，再生成执行提示词。
5. Agent 自验成功后写入 `agent` 评论并把仍处于 `in_progress` 的任务移入 `in_review`。
6. 执行失败或取消后写入 `system` 评论，并把仍处于 `in_progress` 的任务移入 `blocked`。
7. 用户在执行期间人工修正了任务状态时，终态回写保留人工状态，只追加执行记录和评论。
8. 终态写入按 `runId` 幂等，重复 Runtime 事件不能重复评论或重复迁移状态。

Execution 状态：

- `queued`
- `running`
- `waiting_user`
- `waiting_approval`
- `succeeded`
- `failed`
- `cancelled`

本阶段复用现有 durable Runtime Scheduler 与平台全局并发容量，不增加看板自己的业务并发上限。

## 11. 后续自动化兼容边界

后续自动化 loop 继续通过独立服务接入，不改变已经定义的人工语义和单任务执行协议。

仍然后置：

- Cron dispatcher 与候选任务扫描。
- claim 到 Scheduler enqueue 之间的事务 outbox/崩溃恢复，避免进程在两步之间退出后留下活跃记录。
- Runtime 事件投影的持久游标、漏事件对账与终态补偿扫描。
- claim lease、进程中断后的自动恢复。
- 批量/并行派发与容量治理。
- 看板执行器与 CronJob 的显式绑定。
- 任务关系、附件与组织共享看板。

没有确定恢复与调度协议前，不在 Task 表中预埋 `cronJobId / claim*` 等字段。
