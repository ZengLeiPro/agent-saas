# 任务看板定义

## 1. 产品定位

任务看板是个人 Agent 工作事项的人工管理界面，位于「定时任务」下，与任务调度并列。

> 当前实现已迭代到本文第 12 节：包含单任务实施、独立复核、执行恢复、分支字段与 Agent 回写工具；第 2 节保留为首期范围记录。

首期目标是把看板本身定义并落地，不实现自动认领、Cron dispatcher、并行派发、异常恢复等自动化 loop。

- 任务调度回答：什么时候启动什么任务。
- 任务看板回答：有哪些工作事项、当前处于什么阶段、补充了什么上下文、是否已人工确认完成。
- 两者首期互不驱动，不把看板状态写入 CronJob，也不把 Cron 配置复制进看板任务。

## 2. 首期范围

### 包含

- 个人多看板。
- 看板新增、重命名、编辑说明、归档与恢复。
- 任务新增、编辑、拖拽排序、跨列移动、归档与恢复。
- 任务详情、评论、关键词搜索、状态/优先级筛选。
- 乐观更新与 CAS 版本冲突处理。
- 桌面端与移动端可用。

### 不包含

- 自动认领、自动执行、Cron dispatcher。
- 子 Agent 并行派发、claim lease、异常恢复。
- 任务父子、阻塞、关联关系。
- 附件。
- 组织共享看板与成员权限。
- Workflow 画布。

## 3. 归属与权限

- 每个看板只归属一个用户。
- 用户可创建多个看板。
- 所有服务端读写同时校验 `tenantId + ownerUserId`。
- 组织管理员和平台管理员默认也不能读取或修改其他用户的个人看板。
- 看板归档后只读；恢复后重新允许写入。
- 任务归档后不出现在默认看板列，可在归档列表恢复。

## 4. 状态机

| 状态值 | 中文 | 定义 |
|---|---|---|
| `backlog` | 需求池 | 已记录，但尚未承诺进入近期处理 |
| `todo` | 待实施 | 已明确需要实施，等待开始 |
| `in_progress` | 实施中 | 已经开始实施 |
| `in_review` | 复核中 | 已提交结果，正在复核 |
| `ready_to_merge` | 待合并 | 复核完成，等待合并交付 |
| `blocked` | 已阻塞 | 因依赖、信息或条件不足无法继续 |
| `done` | 已完成 | 已经人工确认完成 |
| `canceled` | 已取消 | 明确不再继续处理 |

看板列顺序：

```text
需求池 → 待实施 → 实施中 → 复核中 → 待合并 → 已阻塞 → 已完成 → 已取消
```

执行主路径为 `待实施 → 实施中 → 复核中 → 待合并 → 已完成`；执行失败进入已阻塞，任意未完成任务均可人工取消。

首期全部操作都由看板所有者发起，因此允许人工跨状态纠正和重新打开；服务端记录新状态、Actor、时间与版本，不额外限制跳转路径。后续接入 Agent 工具时，再为 Agent Actor 增加严格转换约束。

## 5. 优先级

| 优先级值 | 中文 |
|---|---|
| `urgent` | 紧急 |
| `high` | 高 |
| `medium` | 中 |
| `low` | 低 |
| `none` | 无 |

默认 `none`。优先级不自动改变排序，用户拖拽顺序是列内展示真相。

## 6. 数据对象

### 6.1 Board

公开 API DTO（与共享类型 `TaskBoard` 一致）：

- `id`
- `name`
- `description?`
- `version`
- `archivedAt?`
- `createdAt`
- `updatedAt`

仅持久化层内部使用、不返回前端：

- `tenantId`
- `ownerUserId`
- `nextTaskNumber`

规则：

- `tenantId + ownerUserId` 是服务端所有查询的权限边界，不作为客户端可依赖的数据字段。
- 同一用户的活跃看板名称不可重复。
- 新建看板默认名称由用户输入，不自动生成隐式默认看板。
- `nextTaskNumber` 只增不减，用于生成看板内稳定任务编号；它是编号分配器状态，不属于公开 API。

### 6.2 Task

- `id`
- `boardId`
- `identifier`，格式为 `TASK-{number}`，在看板内唯一
- `title`
- `description`
- `branch?`，Agent 实施、独立复核或合并时使用的 Git 分支，可由用户填写或 Agent 回写
- `attachments[]`
- `status`
- `priority`
- `labels[]`
- `sortOrder`
- `dueAt?`
- `commentCount`，只读聚合字段
- `version`
- `archivedAt?`
- `createdAt`
- `updatedAt`

首期不放入 `cronJobId / runId / sessionId / claim*`。这些字段只有在自动化 loop 的执行协议确定后才增加，避免现在用假设污染模型。

### 6.3 Comment

- `id`
- `taskId`
- `body`
- `authorType`：`user | agent | system`
- `authorId`
- `authorName`
- `version`
- `createdAt`
- `updatedAt`

公开评论接口只允许用户新增 `user` 评论；`agent` 与 `system` 仅由服务端执行闭环写入。评论编辑和删除后置，避免修改历史上下文。

### 6.4 Execution

- `id`
- `taskId`
- `runId`
- `sessionId`
- `status`
- `purpose`：`work | review`
- `requestedBy`
- `error?`
- `startedAt?`
- `finishedAt?`
- `createdAt`
- `updatedAt`

Execution 是任务与 Runtime Run/Session 的独立关联记录。Task 只表达业务状态，Execution 只表达某次 Agent 尝试；一个任务可随实施、复核与返工产生多次历史 Execution，但同一时刻只能有一条活跃记录。`purpose` 明确区分实施与独立复核，不能依赖任务标题猜测。

## 7. 并发与排序

- Board、Task、Comment 都带从 `1` 开始的 `version`。
- 更新必须提交 `expectedVersion`。
- 版本不一致返回 HTTP 409，响应带当前对象，前端提示后重拉。
- 冲突后前端仅保留用户实际修改的 dirty 字段，其他字段采用服务端 `current`；重试只提交 dirty 字段，不能用旧整表单覆盖并发修改。
- 新任务默认追加到目标列末尾。
- 拖拽排序采用相邻 `sortOrder` 中点；必要时服务端对单列重新编号。
- 前端先乐观移动，失败后恢复旧快照并刷新当前看板。

## 8. 页面结构

### 8.1 入口

「定时任务」页面内增加二级菜单：

- `任务调度`：现有页面，URL `/cron`
- `任务看板`：新增页面，URL `/cron?view=board`

不新增一级 `AppTab`，不改造全局侧栏层级。

### 8.2 桌面端

- 顶部：二级菜单、当前看板选择、搜索与筛选。
- 主区：八列横向滚动看板。
- 卡片：编号、标题、优先级、标签、截止时间、评论数。
- 点击卡片：右侧详情面板。
- Header 操作：刷新、新建任务；看板管理放在当前看板菜单。

### 8.3 移动端

- 二级菜单与看板选择保留。
- 状态列改为单列状态切换，不强制横向展示八列。
- 任务详情使用 Dialog/Sheet。
- 不依赖 hover 才能出现关键操作。

## 9. REST 边界

基础路径：`/api/taskboard`

### Board

- `GET /boards?includeArchived=false`
- `POST /boards`
- `PATCH /boards/:id`
- `POST /boards/:id/archive`
- `POST /boards/:id/restore`

### Task

- `GET /boards/:boardId/tasks?includeArchived=false`
- `POST /boards/:boardId/tasks`
- `GET /tasks/:id`
- `PATCH /tasks/:id`
- `POST /tasks/:id/move`
- `POST /tasks/:id/archive`
- `POST /tasks/:id/restore`

### Comment

- `GET /tasks/:id/comments`
- `POST /tasks/:id/comments`

### Agent Execution

- `GET /tasks/:id/executions`
- `POST /tasks/:id/execute`，请求体接受 `expectedVersion + purpose?`

Task 的 POST/PATCH 接受 `branch`；PATCH 传 `null` 表示清除。所有写接口使用 Zod 严格校验；PATCH 不接受所有权、版本、创建时间等服务端字段。

## 10. Agent 实施与独立复核闭环

实施由用户或任务工具触发；实施成功后，系统自动派发同一任务的复核：

1. `todo` 可启动 `purpose=work` 的实施 Execution，并进入 `in_progress`。
2. 实施成功时，服务端在同一事务内写入交付评论、把任务移入 `in_review`，并创建唯一的 `purpose=review` Execution 与 outbox；事务提交后立即尝试派发，失败由恢复周期补派。
3. 复核 Execution 启动和运行期间任务保持 `in_review`，不会临时回到 `in_progress`；同一任务同时只允许一条活跃 Execution。
4. Execution 独立保存 `runId / sessionId / status / purpose`，不把运行字段塞回 Task；work 与 review 延续既有 Session 复用方式。
5. Runtime Worker 真正 wake 前重新读取任务、分支和最新评论，再按 purpose 生成实施或复核提示词。
6. 复核 Agent 只检查、不顺手修改交付：通过时移入 `ready_to_merge`，不通过时退回 `todo`，客观阻塞时移入 `blocked`；不得直接移入 `done`。
7. 复核成功结束但未形成明确结论时保持 `in_review`；复核运行失败或取消时进入 `blocked`，不得当作代码复核不通过。
8. 实施失败或取消后写入 `system` 评论并进入 `blocked`，不得创建复核 Execution。
9. 服务端按当前 Execution 的 `purpose` 校验回写：work 不能移入 `ready_to_merge | done`，review 不能移入 `done`。
10. `ready_to_merge` 只表示等待后续集成，不自动合并、清理分支、push `main` 或部署；集成完成并验证后才可另行移入 `done`。
11. 终态写入按 `runId` 幂等；确定性的 review Execution ID、单任务活跃唯一约束和 outbox fencing 保证重复事件、并发回调与重启恢复不会重复派发同一轮复核。

Execution 状态：

- `queued`
- `running`
- `waiting_user`
- `waiting_approval`
- `succeeded`
- `failed`
- `cancelled`

本阶段复用现有 durable Runtime Scheduler 与平台全局并发容量，不增加看板自己的业务并发上限。

## 11. 第三阶段：派发恢复与终态对账

第三阶段补齐单任务执行的两个持久化缺口，并承载实施成功后的定向自动复核；不扫描其他任务列：

### 11.1 Execution Outbox

- 手动认领事务同时写入 Execution、任务阶段和 outbox payload：work 执行 `todo → in_progress`，review 保持 `in_review`；事务提交后才允许派发。
- work 成功终态与自动 review Execution/outbox 在同一事务提交，避免进程在“实施完成”与“创建复核”之间退出造成漏派；恢复周期继续处理 pending outbox。
- 版本化 payload 只保存幂等重建 Session 与 Runtime Run 所需的模型、执行目标、工作区和关联 ID，不保存连接器凭据或密钥；结构或关联字段损坏时失败收口，不永久重试毒消息。
- API 请求内立即尝试一次派发；失败时 Execution 保持 `queued`，错误字段显示“派发重试中”，不提前写失败终态。
- Runtime Scheduler 每次 tick 唤醒独立 single-flight 恢复周期，不在 Scheduler 临界路径等待 outbox 和对账 I/O。
- `runId` 与 `idempotencyKey` 固定；Session 使用跨进程原子 `ensure` 仅首次创建，旧 Worker 不能把完成态改回 `running`。
- Runtime Run 使用 create-only enqueue：同一 `runId` 已存在时只校验关联字段并原样返回，绝不把 `waiting_user / waiting_approval` 恢复为 `pending`；同一幂等键却出现不同 `runId` 时按永久冲突失败收口，不进入瞬时重试。
- 派发使用 60 秒 `leaseId` 租约；旧 Worker 不能用过期 lease 覆盖新 Worker 的 outbox 结果。重试采用 1—60 秒指数退避。
- 派发成功或 Execution 进入终态后，outbox 标记 `dispatched` 并停止重试。

### 11.2 Runtime 终态对账

- live Runtime 事件仍是低延迟主路径。
- 恢复周期认领超过 30 秒仍处于活跃态的 Execution，并以 durable RunStore 为最终事实源；候选使用 30 秒租约和 `lastReconciledAt` 轮转，固定批次不会饿死后续任务。
- `running / waiting_user / waiting_approval` 用于修正遗漏的中间状态；`completed / failed / cancelled / orphaned` 幂等补写任务状态和评论。
- 对账要求 `runId + sessionId + executionId` 三者一致；成功时只从同 Run、同 Session 的持久化事件中提取最后一条完整 `assistant_message`，行为与 live `run_finished` 一致。
- 刚进入 Runtime 终态的 Run 保留 30 秒 live 事件宽限期，避免抢先写入无文本兜底回执。
- 旧版本遗留的活跃 Execution 如果同时没有 outbox 和 Runtime Run，会写系统错误评论并进入 `blocked`，不再永久卡住。
- 所有对账状态和终态写入都校验候选 lease 且要求租约未过期；live Runtime 事件写入会立即使旧对账 lease 失效。
- 多进程可重复执行对账；候选租约 fencing、Execution 行锁和终态幂等保证不会重复评论或覆盖人工状态。

## 12. 统一任务工具与后续任务编排

看板能力并入现有 `CronManage`，以 `target` 区分资源域，避免增加另一个固定工具：

- 缺省 `target=cron`，原有 `list / create / update / delete / run` 行为不变。
- `target=taskboard` 只允许 `taskboard-*` Execution 调用；支持受限的 `list / create / update / move`，不能直接 `execute` 已有任务。
- 服务端按 `runId` 反查执行上下文并 fencing：`list` 只能读取当前任务详情（含评论与 Execution 历史）。
- `update` 只能以 CAS 回写当前任务的 `branch`，传 `null` 可清除。
- `create` 只能在当前看板创建 `todo` 后续任务，可携带 `branch`；`dispatch=true` 会立即创建独立 work Session，用于复核、返工、合并等后续事项。
- 只有 `purpose=review` 的活跃 Execution 可 `move` 当前任务到 `ready_to_merge | todo | blocked`；不得移入 `done`，状态决策与 Execution 活跃态校验在同一数据库事务完成。
- 普通 Session 即使已有 `scheduling/CronManage` 权限也不能进入看板域，不会静默扩权；工具使用会话归属者身份且不接受调用方伪造 owner。统一 descriptor 的审计域为 `task.manage`。

独立合并不是 Execution 的特殊分支：Agent 用 `create + dispatch` 创建一条带目标 `branch` 的普通 `todo` 任务。这样合并、复核和返工都使用同一套任务历史、权限、幂等和恢复机制。

## 13. 后续自动化兼容边界

后续自动化 loop 继续通过独立服务接入，不改变已经定义的人工语义和单任务执行协议。

仍然后置：

- Cron dispatcher 与候选任务扫描。
- 自动认领的 claim lease、运行中副作用恢复策略。
- 批量/并行派发与容量治理。
- 看板执行器与 CronJob 的显式绑定。
- 正式的父子任务、阻塞依赖与关系图；当前由普通任务与评论表达。

没有确定自动调度协议前，不在 Task 表中预埋 `cronJobId / claim*` 等字段。
