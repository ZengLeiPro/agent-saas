维护当前会话的计划、进度和可追溯的业务步骤记录。用户可能不打开步骤或详情，不得假定其中的内容已被用户阅读；步骤记录不能替代面向用户的答复或真实确认交互。
用于非平凡的多步骤工作（通常 3 步以上真实步骤）、多个用户请求、用户明确要求 todo/checklist，或需要在会话里持续展示业务阶段时。不要用于单步、琐碎或纯信息性请求，也不要在每次工具调用后都更新。

所有步骤都必须设置 `kind: "business"`，并提供稳定且跨更新不变的 `id`。不存在普通 `task` 模式；基础步骤只需 `id`、`kind`、`content`、`status`，其余富字段按需使用。
多步骤任务在开始实际执行前就发送首个快照亮出完整计划（第一步置 `in_progress`），随执行逐步更新；不要接近完成时才补记步骤——补记的步骤流没有过程可归属，时间线会失真。

每次调用发送完整列表并整体替换上一版。
`status` 可用：`pending`、`in_progress`、`waiting`、`blocked`、`completed`、`failed`。仍在自动执行时保持恰好一项 `in_progress`；等待用户、业务阻断或失败时允许没有 `in_progress`。
可选字段：

- `activeForm`：步骤进行中显示的当前动作；
- `outcome`：一句话业务结果/现状 `{text≤120字, tone?, stat?}`。用于用户查看步骤时快速理解现状，应自包含并保留相关关键数字（如「17/18 张通过，1 张税号过期退回」），但不得假定它在主对话区可见。`tone`：完成但有例外（漏记/差异/部分失败）必须 `"warn"`，彻底失败或不可信用 `"fail"`——不允许用干净的「已完成」掩盖例外。`stat`：分流计数徽标（如 一致 61 / 差异 19 / 无法匹配 6）；每项可选 `verdict`（`"pass"` / `"fail"` / `"neutral"`）显式声明该徽标是好消息、坏消息还是纯计数，不给则由展示层按文本保守判别（含数字的值一律按纯计数处理）。步骤进入 `completed`、`failed`、`blocked` 或 `waiting` 时应带 outcome；`waiting` 写清等待对象和原因，时间仅在已知时填写。`pending` 无需编造结果；
- `detail`：只承载非表格的结构化业务摘要，用于单条判定、缺口、风险、引用和少量上下文；顶层 `detail` 不接受 `section`，且最多一条 `verdict`，也不接受 `k/v`、树形键值或字段网格；
- `display`：只接受 `facts`、`list`、`comparison`、`checklist` 四种业务语义，不接受 `callout`、`records` 或 `layout` 等视觉实现字段。每个块的 `title` 都必填，使用简短业务动作或结果名称（如「核对工作树状态」「已创建提交」），不得使用空泛的「详情」「结果」；
  - `facts`：相互独立的短字段，如对象属性、提取结果、关键指标；展示层会在字段紧凑时自动使用网格，否则回退逐行展示；
  - `list`：普通清单、命中列表、提交记录；
  - `comparison`：预期/实际或变更前后的差异对照；每项使用 `label`、`baseline`、`current`、`delta`，可用 `status` 标记差异判定；
  - `checklist`：两项及以上的逐项判定，`item.status` 使用 `pass` / `fail` / `warn` / `pending`；单项判定继续使用顶层 `detail.verdict`；
- `evidenceRefs`：支撑该步骤的真实对象、来源或回执的短引用（对象 ID/单据号/文件名/路径，每条尽量 ≤40 字）。它是引用不是内容：不要塞整句话，更不要塞数据明细——数据按语义写入 `detail` 或 `display`。

步骤转为 `completed`/`failed`/`blocked`/`waiting` 时，该次快照携带的 `outcome`/`detail`/`display`/`evidenceRefs` 会保存在步骤记录中，可能需要用户打开详情才能看到。因此状态变化的那次调用必须带上该步骤当前准确的业务内容，但不能把写入快照当成已向用户交付。`content` 是稳定的步骤名，不要把结果写进 `content`，结果一律写 `outcome`。
在每个步骤状态变化时更新一次快照即可；步骤进行中的普通工具调用不需要也不应该触发列表更新。
执行中发现新信息导致计划变化时，应新增、删除、重排、拆分或合并步骤；未变化步骤保持原 `id`，不要机械坚持初始计划。
执行途中需要用户作出决定时，应立即通过 AskUserQuestion / permission_request 等真实交互通道提出，写清决策内容及必要上下文，并在等待前将相关步骤更新为 `waiting`、在 outcome 中写明原因。不得仅在 outcome、detail 或 display 中留言，也不得等到最终答复才提出阻塞性问题。通道不支持真实交互时，应在面向用户的答复中直接提问并停止依赖该答案的工作。等待外部系统时也可使用 `waiting`，但不得描述成等待用户确认。不要在 Todo 中伪造按钮；没有真实依据时不得填写 evidenceRefs，也不得把步骤标成已确认。
面向用户的最终答复必须独立完整，包含回答原始请求所需的结论、关键结果、重要异常、未完成事项及交付物入口。不得因这些信息已写入 TodoWrite 而省略；无需重复完整执行过程和原始明细。

步骤完全做完后立即标记 `completed`，再把下一项置为 `in_progress`。结束本轮前，根据实际执行情况更新完整步骤快照；尚未执行的步骤保留 `pending`，仍需用户输入或存在阻塞的步骤如实标记，不得为结束展示而标记 `completed`。测试失败、实现不完整、依赖/文件缺失或仍有阻塞/报错时，不得标记 `completed`。移除不再相关的条目。返回持久化后的列表。
